# Schema candidates: which dictionary to describe next

[日本語版](SCHEMA_CANDIDATES_ja.md)

FoDE's Detail pane explains the key under the cursor — what it means, what values
it accepts, which releases have it — from the schema modules in `schemas/`.
A dictionary with no module gets a blank pane. This page ranks the dictionaries
that have no module yet, and says for each whether it should be **hand-written
here** or **generated by foamlore**, because that
choice is not a matter of taste: it follows from the shape of the dictionary.

For how to write one, see DEVELOPER.md's "Schema system". Read the table-key
convention there before you start — a module whose keys are spelled
`"<key>.<parent>"` instead of `"<parent>.<key>"` loads, passes naive unit tests
and is reachable from nothing, which is exactly what happened to `fv_schemes.py`
for its whole life.

## Where coverage stands

Six dictionaries have modules: `controlDict`, `fvSchemes`, `fvSolution`,
`blockMeshDict`, `snappyHexMeshDict`, and `turbulenceProperties` +
`momentumTransport` (the last two from foamlore's generator). FoDE's file list
offers 105 names, so most of what a user can open has no schema behind it.

## How this list was ranked

Two numbers per candidate, both measured rather than estimated:

- **How often a case has one** — the number of files with that name in
  `tutorials/`, counted separately for Foundation 12 and OpenCFD v2606, because
  a dictionary common on one fork can be absent from the other. See
  [OPENFOAM_VERSIONS.md](OPENFOAM_VERSIONS.md) for why the two columns differ so
  much.
- **How many distinct keys it has** — a rough count of the key names appearing
  across every instance in the tutorials. This is the effort side: it is the
  number of `KeySchema` entries somebody has to research and write.

A third, unquantified factor decides ties: whether FoDE already understands the
file for another reason. `topoSetDict` and `setFieldsDict` already have their
source types and geometry keywords enumerated in code, because the 3-D viewer
draws them.

## Tier 1 — hand-write these in FoDE

A bounded key set owned by one utility, with little or no fork divergence. There
is nothing to generate: the keys can be counted on paper, and the value of the
entry is the prose explaining the key, which no generator produces.

| dictionary | OF12 | v2606 | keys | note |
|---|---:|---:|---:|---|
| `system/decomposeParDict` | 106 | 362 | 25 | the single most common dictionary after the core four; `method` is a closed choice list (`scotch`, `hierarchical`, `simple`, `kahip`, `metis`, `none`) and the per-method coefficient blocks are small |
| `system/setFieldsDict` | 64 | 134 | 30 | the region source types are already enumerated in `foam/set_fields_extractor.py` for the 3-D viewer |
| `system/topoSetDict` | 34 | 137 | 53 | same, in `foam/topo_set_extractor.py`; the `source` value list and each source's geometry keys are already written down as code |
| `constant/g` | 137 | 232 | 9 | an afternoon, and it is in nearly every case |
| `system/fvConstraints` | 52 | 0 | 25 | Foundation only; pairs with `fvModels` in Tier 2, but the constraint side is a short closed list |
| `system/meshQualityDict` | 16 | 41 | 20 | **nearly free**: `schemas/snappy_hex_mesh_dict/_mesh_quality.py` already describes these exact keys for the `meshQualityControls` block. Adding a `TARGET_FILES` tuple so the module also answers for the standalone file is a few lines |
| `system/createPatchDict` | 6 | 48 | 14 | |
| `system/surfaceFeatureExtractDict` / `surfaceFeaturesDict` | 13 | 49 | 17 / 13 | one module, two `TARGET_FILES` names — see the fork table in OPENFOAM_VERSIONS.md |
| `system/createBafflesDict` | 18 | 13 | 16 | |
| `system/extrudeMeshDict` | 14 | 17 | 36 | more keys than its frequency justifies; do it after the cheaper ones |
| `system/refineMeshDict` | 3 | 10 | 20 | cheap filler |
| `constant/regionProperties` | 0 | 19 | 8 | current on OpenCFD; Foundation stopped shipping it after v10 |
| `system/meshDict` | 0 | 22 | 8 | cfMesh, OpenCFD only |
| `system/faSchemes` / `faSolution` / `faMeshDefinition` | 0 | 17 | 14 / 36 / 9 | finite area; OpenCFD only. `faSchemes`/`faSolution` mirror their `fv` counterparts closely enough that the existing modules are a starting point, not a template to copy |
| the sampling dicts (`sample`, `probes`, `surfaces`, `singleGraph`, `sampling`, `cuttingPlane`) | few | few | — | low counts, but FoDE renders their geometry in the 3-D viewer, so a user is looking at them with the Detail pane open |

Suggested order: `meshQualityDict` (a tuple), then `decomposeParDict` and `g`
(high frequency, small), then `topoSetDict` and `setFieldsDict` (the extractors
already did the research), then the rest as time allows.

## Tier 2 — generate these with foamlore

The valid values live in a C++ class hierarchy resolved at runtime, the set
differs between forks and grows between releases, and the useful content is
coefficient names, defaults and the prose OpenFOAM ships beside them. This is
exactly the shape foamlore's generator was built for — it produced 11,557 lines
covering 29 turbulence models across 17 releases, which nobody was going to hand-write.

| dictionary | OF12 | v2606 | why generated |
|---|---:|---:|---|
| `constant/physicalProperties` / `transportProperties` + `thermophysicalProperties` | 165 | 491 | the top of the list by a distance. `thermoType` is a seven-slot runtime-selection combination (`type`/`mixture`/`transport`/`thermo`/`equationOfState`/`specie`/`energy`); the valid combinations are what a user actually gets wrong, and they are only knowable from `src/thermophysicalModels` |
| `constant/dynamicMeshDict` | 40 | 118 | motion solvers and topology changers by RTS, and Foundation restructured the mechanism after v10 — a hand-written module would be stale within a release |
| `constant/fvOptions` / `fvModels` | 72 | 43 | one fork's `fvOptions` is the other's `fvModels` + `fvConstraints` ([OPENFOAM_VERSIONS.md](OPENFOAM_VERSIONS.md)), and each source type is its own class with its own keys |
| `constant/radiationProperties` | 8 | 72 | radiation model + scatter/absorption sub-models, all RTS |
| `constant/combustionProperties`, `chemistryProperties` | 16, 10 | 45, 42 | same shape, lower value; do them only if the generator is already scanning that tree |

**The cost gate.** foamlore's `facts/tools/fetch_sources.sh` sparse-checks out
only `src/TurbulenceModels` / `src/MomentumTransportModels` and
`src/finiteVolume/finiteVolume` across its checkouts. Every family above starts
with fetching a new subtree for all of them and writing a registry for it. That
is worth doing once for the thermophysical family; it is not worth doing for a
nine-key file. **Do not** hand-edit a generated module in `schemas/` to work
around this — they carry a GENERATED banner and a test asserts it. Requests to
the generator go in foamlore's own spec.

## Deliberately not worth a schema

- **`system/changeDictionaryDict`** (55 cases on v2606) — its keys are the
  user's own field and patch names. There is nothing general to say about them.
- **`system/functions`** and the function-object configs — the key set is the
  union of every function object OpenFOAM ships, which is open-ended and
  documented per object in `etc/caseDicts/postProcessing/`. If this is ever
  wanted, the shape is a reader of those files, not a hand-written table.
- **Files that only look like dictionaries** — `constant/foam.inp` and
  `foam.dat` are Chemkin data, and FoDE deliberately does not list them.

## Before you start

Run `tests/schemas/test_schema_coverage.py`. It parses real tutorial fixtures,
walks them the way the Detail pane does, and enforces a per-dictionary coverage
floor — which is what catches a module that is present, imported and reachable
from nothing. Add a floor for your new dictionary in the same change; the floors
are meant to sit just under current coverage and only ever go up.
