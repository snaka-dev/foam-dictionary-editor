## 何を見せるかの選定

長い動画 1 本ではなく短い動画を複数にします。それぞれが別の問いに答えていて、すべての問いを持っている人はいないからです。最初の 3 本は一般的な主張 — *なぜこれを使うのか*、*どう見えるのか*、*自分の作業にどう合うのか* — で、FoDE を見たことがない人に見せるならこの 3 本です。残りはそれぞれ 1 つの辞書ファミリーを掘り下げたもので、その問題を自分が抱えていると既に分かっている人向けです（表面まわりのメッシュ生成、サンプリング、マルチリージョン）。最初の 1 分で離脱した人も、主張そのものは見終えています。

**動画 7 は意図的な例外**で、他のどれよりも 3 倍以上長くなっています。これは SoftwareX 論文の Appendix A — icoFoam/cavity のワークスルー — をそのまま収録したもので、付録を読み終えた人が想像で補う代わりに実際に見られるようにするためのものです。他を短く保つ理由はここには当てはまりません。この動画の視聴者はすでに試すと決めていて、ケース 1 本が端から端までどう進むのかを知りたがっており、それは 1 分では答えられない問いだからです。論文からリンクすべきはこの動画で、逆に最初に見せる動画としては不向きです。

各シーンは、OpenFOAM インストール側のケースよりリポジトリ自身の `tutorials/` のケースを優先します。同梱ケースであれば**リポジトリを clone した誰もが同じ動画を再生できます**し、収録も再現可能になります。ドライバは収録のたびにケースをスクラッチディレクトリへコピーするので、`blockMesh` を実行する動画は毎回メッシュのないケースから始まります。

## 動画 1 — 編集し、見て、実行する（`damBreak`、約 65 秒）

**シーン:** `damBreak-end-to-end`。**ケース:** 同梱の `tutorials/damBreak`。**主張:** 辞書と、それが記述する形状と、それを読み込むツールは 1 つのループであり、FoDE はそのループを閉じる。

レイアウトは side-by-side。ツリーと 3D ビューを同時に画面に出します。片方の編集がもう片方に届くことがこの動画の眼目だからです。詳細ペインは畳んで、両者に幅を回します。

| 時刻 | ショット | 画面 | ナレーション |
|---|---|---|---|
| 0:00 | 開始 | ケースが読み込まれ、`blockMeshDict` が開かれ、ツリーの横にブロックメッシュが描かれている | これは OpenFOAM のケース（damBreak チュートリアル）を FoDE で開いたところです。左に辞書のツリー、右にはそれが記述するメッシュが描かれています。 |
| 0:04 | `setFieldsDict` を開く | ファイルをクリック。メッシュの中にオレンジの水柱が現れ、`alpha.water=1 (clipped)` のバッジが付く | setFieldsDict を開くと、それが初期化する領域がそのメッシュ上に直接描かれます。 |
| 0:09 | `box` 行を選択 | ツリー行がハイライトされ、下のエディタが 26 行目までスクロールしてその行をマークする | それを定義している box を選ぶと、下のエディタがその行へジャンプします。 |
| 0:15 | 値を編集 | Value セルをダブルクリックし、`(0 0 -1) (0.35 0.4 1)` を入力 | 水柱を変えてみます。もっと広く、もっと高く。 |
| 0:17 | オーバーレイが追従 | Enter。オレンジの箱が大きくなり、エディタの行も書き換わり、3 つのビューが一致する | オーバーレイが編集に追従します。再実行も、エクスポートも、座標の当てずっぽうもありません。 |
| 0:22 | 保存 | **Save File** | ファイルを保存します。 |
| 0:26 | blockMesh を実行 | **Tools > Run blockMesh…**、続いて **Run** | 場を設定する前にメッシュが存在している必要があるので、blockMesh を実行します。 |
| 0:31 | 実行される | Terminal タブが埋まり、完了と同時にファイル一覧に `constant/polyMesh: 2,268 cells` のインジケータが現れる | ケースディレクトリの Terminal タブで実行され、出力はログに tee されます。 |
| 0:40 | setFields ダイアログ | 値が累積するという警告、既定でチェック済みの **Restore 0/ from 0.orig/ first**、そしてコマンドプレビュー `rm -rf 0 && cp -r 0.orig 0 && setFields 2>&1 \| tee log.setFields` | 次は setFields です。フラグを覚えておくよう求めるのではなく、ダイアログが提示し、実際に送るコマンドをそのまま表示します。setFields は 0/ をその場で書き換えるので、先に 0.orig から 0/ を復元するかを尋ねます。既定でチェック済みで、コマンドにも現れています。 |
| 0:48 | 実行される | `Selected 1012/2268 cells` — この数は 0:15 で編集した box から導かれたもの | 実行します。 |
| 0:57 | ログサマリ | **Tools > View Log Summary…**: ユーティリティ、ビルド、ケース、末尾、`Result: OK` | そして実行が残したログは、レポートに凝縮されます。何が動き、何を出力し、どんな警告を出したか。 |

再編集するとしても守るべきショットは 2 つです。**0:17**。3 者が同期する様子は他のエディタにないものだからです。そして **0:48**。`Selected 1012/2268 cells` は 0:15 の編集が数値になって返ってきたもので、ループが閉じたと主張するのではなく、閉じるところが見えるからです。

各ステップの `then`（表示時間）はナレーションの長さに合わせ、読み上げられる速度を目安にしています。3 文のナレーションが付くステップ（setFields ダイアログ）は 8 秒、`ファイルを保存します。` は 2 秒です。

レイアウトは **BlockMesh** タブを全幅で。ここでは 3D ビューがツリーの引き立て役ではなく、主張そのものだからです。

## 動画 4 — 表面のまわりにメッシュを切る（`motorBike`、約 57 秒）

**シーン:** `motorBike-snappy-overlay`。**ケース:** 収録マシンの run ディレクトリ（`{cases}`）にある `motorBike`。ケースが同梱されていないため、clone しただけの状態では再現できない唯一の動画です。**主張:** `snappyHexMeshDict` の大半は目に見えないものへの参照であり、FoDE はそれを描く。

| 時刻 | ショット | 画面 | ナレーション |
|---|---|---|---|
| 0:00 | 開始 | 背景ブロックメッシュの中に motorBike 表面（ティール）、紫の `refinementBox`、`locationInMesh` のマーカー | snappyHexMesh は表面のまわりにメッシュを作りますが、その辞書の大半は目に見えないものへの参照です — ジオメトリファイル、リファインメント領域、どちら側が流体かを決める点。ここで開けば、それらが描かれます。切り出される元になる背景メッシュの中に。 |
| 0:06 | 回転 | シーンが回る | このバイクは辞書が指定している triSurface で、constant/triSurface から解決されて読み込まれています。 |
| 0:12 | ズーム | スクロールで寄ると、バイクの形が見えてくる | 寄ってみると、代役のバウンディングボックスではなく本物の表面です。 |
| 0:19 | `snappyHexMesh ▾` メニュー | カテゴリごとに分類された行、surface/region/geometry の凡例、keep-point の行 | 行は辞書での使われ方で分類されています — スナップ先の surface、リファインメントの region、そして keep-point。メッシュがおかしくなったときに効いてくるのがこの区別だからです。 |
| 0:26 | box だけ | バイクのチェックを外し、領域内にリファインメントボックスだけが残る | バイクを隠すとリファインメント領域だけが残ります。実際に確認したいのはこれです。リファインすべきものを囲めているか、そもそも背景メッシュの中に入っているか。 |
| 0:35 | ツリーからエディタへ | `refinementRegions/refinementBox` を選ぶと、エディタがそこへスクロールする | ツリーで領域を選ぶと、エディタがそれを定義しているエントリへ移動します — リファインメントレベルと、内側と外側のどちらをリファインするかを決める mode。 |
| 0:44 | keep-point | `locationInMesh` のマーカー | そしてこのマーカーが locationInMesh です。snappyHexMesh に表面のどちら側を残すかを教える、たった 1 つの点。逆側に置けば、メッシャーはバイクではなく領域の方を嬉々として消します。辞書ではたった 1 行ですが、いまはそれを目で見られる場所にあります。 |

再編集の前に知っておくべき点が 2 つあります。

**0:26 でカメラが引き戻ります。** 形状を隠すと再描画が走り、すべての描画は `reset_camera()` で終わるため、0:12 のズームは取り消されます。収録側で直すべき不具合ではなく、パネルの仕様です。ここではたまたま、その直後のナレーションが「ボックスは領域全体の中に入っているか」を問うので、引いた画角の方が答えになっています。

**回転は `"ticks": 6` に設定しています。** ドラッグの 1 刻みごとに再描画が走り、この表面は重いため、既定の粒度では 1.4 秒の回転が 24 秒になりました。刻みを減らして 1 回を大きくすると滑らかになります。遅いのは動きではなくフレームだからです。

`motorBike` のサンプリング辞書は `system/cuttingPlane` ですが、FoDE はこれをサンプリング辞書として認識しません（`SAMPLING_DICT_NAMES` は `sample`・`probes`・`surfaces`・`singleGraph`・`controlDict`）。そのためこの動画にサンプリングのオーバーレイは出てきません。サンプリング側の題材は同梱の `tutorials/samplingShapes` で、そのために作られたケースです。

## 動画 5 — 3 つのファイル、1 つのビュー（`samplingShapes`、約 50 秒）

**シーン:** `sampling-three-files-one-view`。**ケース:** 同梱の `tutorials/samplingShapes`。**主張:** サンプリングは、定義が仕様上あちこちのファイルに散らばる唯一のオーバーレイであり、パネルはそれを、どこに書いたかを覚えていなくても 1 つに組み立て直す。

| 時刻 | ショット | 画面 | ナレーション |
|---|---|---|---|
| 0:00 | 開始 | 3×3×3 のブロックの中に probe の点、sample のチューブ、2 枚の plane の円盤。それぞれにバッジ | サンプリングはこれらの辞書の中で異色の存在です。自分専用のファイルを持ちません。controlDict の中の function object としても、独立した辞書としても書けますし、リストの書き方も 2 通りあります。このケースはその 3 つすべてに定義を分散させていて、パネルはそれを 1 つのシーンとして描きます。 |
| 0:06 | 回転 | シーンが回る | probe の位置は点マーカー、サンプリング線はチューブ、サンプリング平面は円盤として描かれます。 |
| 0:10 | `sample ▾` メニュー | 各行に取得元のタグ: `nearWallProbes · probes [controlDict]`、`topSpan · lineUniform [sample]`、`midCut · cuttingPlane [surfaces]` … | そして各行が、どこから来たかを告げます。nearWallProbes は controlDict から、topSpan と scatter は sample から、midCut と lowCut は surfaces から。3 つのファイル、1 つのビュー。どれにどれを書いたかを覚えておく必要はありません。 |
| 0:16 | 2 つのチェックを外す | `topSpan` と `scatter` が消え、Escape で結果が見える | 取得元のファイルが何であれ、他のオーバーレイと同じように切り替えられます。 |
| 0:26 | Show all | 元に戻る | |
| 0:31 | クリッピング | 2 枚の plane に `(clipped)` バッジ | 2 枚の平面はどちらも clipped と表示されますし、常にそうなります。サンプリング平面は無限に広がるので、この円盤は自前の縁を持つ形状ではなく、いま見ているメッシュに合わせて切られた表示上の便宜だからです。 |
| 0:42 | probe の出どころ | Tree タブ、`controlDict` を開き、`functions > nearWallProbes > probeLocations` を 3 点とともに選択。エディタが該当行をハイライト | そしてこれが 3 つのうちの 1 つ。controlDict の function object としての probes と、あのマーカーを今の位置に置いている点の座標です。ソルバーが受け付ける場所ならどこに書いてもよく、それでいてソルバーを一度も走らせる前に描かれます。 |

この動画を支えているのは **0:10** です。同じリストの中に `[controlDict]`・`[sample]`・`[surfaces]` が並んで見えること。その前はすべて前振りで、その後はすべて裏付けです。再編集で何かを削るなら、回転を削ってください。

締めのショットがこの動画の中で最も地味なのは意図的です。40 秒かけて積み上げてきた 3D ビューではなく、ツリーとエディタで終えること自体が主張になっています。あの絵はこの 3 つのファイルから来ていて、これがそのうちの 1 つです。

## 動画 6 — 5 つのメッシュ、1 つのケース（`snappyMultiRegionHeater`、約 31 秒）

## 収録

```bash
DISPLAY=:1 python3 tools/demo_driver.py --list
```

まずリハーサル。同じ流れを収録なしで実行するので、タイミングの調整が安上がりです:

```bash
DISPLAY=:1 python3 tools/demo_driver.py damBreak-end-to-end
```

そして収録します。ファイル名を省略すると `docs/demo/<シーン名>.mp4` に出力されます。`.gif` を指定すると、同じ収録を 2 パスのパレットエンコードにかけ、README 用のループ動画にします:

```bash
DISPLAY=:1 python3 tools/demo_driver.py damBreak-end-to-end --record
```

`cavity-full-workflow` だけは他と違って 2 つ前提があります。起動元のシェルで OpenFOAM を**source しておく**こと。ParaView のショットは `PATH` 上の `paraFoam` を探し、見つからなければ何も読み込んでいない素の `paraview` に静かにフォールバックするからです。もう 1 つは、収録がウォッチドッグの既定値より長いので、上限を上げることです:

```bash
source /usr/lib/openfoam/openfoam2512/etc/bashrc
LIBGL_ALWAYS_SOFTWARE=1 DISPLAY=:1 python3 tools/demo_driver.py cavity-full-workflow \
    --record --max-seconds 420
```

`LIBGL_ALWAYS_SOFTWARE=1` は ParaView のためのものです。ネストされたディスプレイ上で描画するので、そこにハードウェア GL はありません。このシーンには FoDE 自身の 3D パネルは出てこないので、他に代償を払うものはありません。

### ファイルの置き場所

**動画はリポジトリで管理しません。** `docs/demo/*.mp4` は gitignore 対象で、隣の `.gif` や `.webm` も同様です。動画はシーンから再生成できる派生物であり、しかも動画は差分圧縮が効かないため、撮り直しを管理下に置けばそのたびに数 MB のブロブが履歴に永久に積まれます。撮り直しを安くするためのツールであることが、そのまま出力を保存するコストを高くしています。7 本 1 セットで、スクリーンショットギャラリー全体の数倍のサイズです。

**隣の `.srt` ファイルは管理します。** 1 本あたり数 KB のプレーンテキストで差分も読め、動画と一緒にアップロードする字幕トラックそのものだからです。各ファイルは収録元のテイクと対応しているので、撮り直したら再アップロードもセットで行ってください。

**公開版は YouTube に置きます。** README や issue、リリースノートからリンクすべきなのはそちらです。GitHub は Markdown 内でリポジトリ相対の `.mp4` を再生しないので、動画を管理下に置いてもリンク以上の利点はありません。

収録は、起動元のデスクトップではなく**収録専用のネストされたディスプレイ**（Xephyr）上で行われます。ステップは実際のマウス・キーボード入力なので、使用中のデスクトップでは別のウィンドウが最前面に上がってクリックを奪い、入力はフォーカスの移った先へ流れてしまいます。設定は不要で、これが既定の動作です。例外は `--stage` で、シーンの開始状態でウィンドウを開いて停止し、目の前のディスプレイ上で手作業収録に使えるようにします。

収録のたびに、動画の横に `.srt` が書き出されます。ナレーションが対応するフレームに合わせてタイミング付けされたもので、読み上げ用の台本であり、同梱する字幕トラックではありません。ツール自身が音声を出すことはありません。

**動画に収録者の名前を映してはいけません。** ギャラリーと同じ規則であり、シーンがケースをその場で開かず `/tmp` にコピーする理由でもあります。Log Summary ダイアログはログファイルからケースのパスをそのまま表示し、このリポジトリはホームディレクトリ以下にあるからです。
