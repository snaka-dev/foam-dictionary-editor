# Release Notes

## v1.13.0 — 2026-08-07

### New features

- **The Detail pane now shows what OpenFOAM says about a coefficient, not only what its default is** — a value tells you what the solver will do; it cannot tell you what the coefficient means or when to change it. OpenFOAM's own headers do, and foamlore now extracts that prose and carries it into the generated schemas, quoted verbatim with the file and line it came from. Selecting a `<model>Coeffs` dictionary shows the model's description from its header — every one of the 29 models has one — with the paper that defines it in the Note row, so `kEpsilonCoeffs` cites Launder & Spalding and `GEKOCoeffs` cites Menter & Matyushenko (2025). Selecting a coefficient that upstream documents on its declaration leads with that: `F3` reads "Flag to include the F3 term" before the mechanical default sentence, and 257 coefficients carry one.

  The case that prompted it is rarer and more useful than either. GEKO's `CFbLam` is written in the source as `1.0  // increase to 25 in case of transition simulations (MM:p. 4)` — the comment says *when* to change the coefficient, and `MM` is a tag into that model's own reference block. That note is now on the key, and the citation resolves against the reference shown on the dictionary above it. Long quotes are trimmed for the pane and marked as trimmed; foamlore's `get_fact` returns the full text with its citation.

- **The model selector describes each model, in OpenFOAM's own words** — a normal `constant/turbulenceProperties` is five lines and names no coefficient dictionary at all: `simulationType RAS;` and a `RAS { RASModel kEpsilon; turbulence on; printCoeffs on; }` block. Everything the entry above describes hung off `kEpsilonCoeffs` — a key that exists only in a case that overrides a default, which most cases do not — so in the commonest case none of it was reachable. Selecting `RASModel` (or `model`, or their LES spellings) now shows, for the value you pick, the model's description from its own header and the paper that defines it: `kEpsilon` reads "Standard k-epsilon turbulence model for incompressible and compressible flows including rapid distortion theory (RDT) based compression term" and cites Launder & Spalding (1972). All 27 model choices in the two selectors are covered; `laminar` is not a model class, so it keeps the short hand-written line. The choice list itself, and which fork ships which model, are unchanged — they are facts about the dictionary rather than about any model, and stay hand-maintained.

- **Turbulence-model coefficient help now covers 29 models, not three** — the schema modules generated by the sibling foamlore project documented `kOmegaSST`, `kEpsilon` and `SpalartAllmaras`, because that project had one hand-written extractor script per model and each new one cost a new script. It now has a registry where a model is one table row, and coverage went to **16 RAS models and 13 LES/DES models** — every model either fork ships — measured across all seventeen releases: `kOmega`, `kOmega2006`, `realizableKE`, `RNGkEpsilon`, `LaunderSharmaKE`, `LRR`, `SSG`, `EBRSM`, `GEKO`, `kEpsilonPhitF`, `v2f`, `kOmegaSSTLM`, `kOmegaSSTSAS`, the `Smagorinsky`/`WALE`/`sigma`/`kEqn`/`dynamicKEqn`/`dynamicLagrangian`/`DeardorffDiffStress` LES set, and the `SpalartAllmaras`/`kOmegaSST` DES, DDES and IDDES families. Select any of their coefficients and the Detail pane names the source default, the releases it exists in, and the constructor it was read from.

  Two things fall out of that scale. A coefficient a model inherits rather than declares is now followed to the base class that declares it — `kOmegaSSTSASCoeffs { betaStar 0.09; }` is a real entry even though `kOmegaSSTSAS.C` does not mention it. And 28 of the 134 coefficient names are read by more than one model — `Cmu` by nine of them — where previously every name had exactly one owner. Written flat inside `RAS { … }`, as OpenFOAM's `optionalSubDict` allows, those names now resolve to a single entry that names every model reading them and offers each model's default separately; written inside a `<model>Coeffs` dictionary, that model's own entry still wins.

### Bug fixes

- **One schema value with a bracket in it no longer switches off syntax highlighting for hundreds of keywords** — the value-keyword highlighter builds its patterns by joining every schema key and choice value with `|`, a thousand at a time, and never escaped them. Every keyword had been a plain identifier, so nothing had exposed it; the first choice value containing a regex metacharacter — `scalar(2)/scalar(3)`, which is genuinely how OpenCFD wrote `sigmaNut`'s default until v2212 — made the whole chunk's pattern invalid, and Qt silently declines to match an invalid pattern. The visible symptom was that `application`, `PCG` and every other keyword sharing that chunk simply stopped being coloured. Alternatives are now escaped, and a choice value that is an expression rather than a word is no longer collected as a keyword at all, since the `(?<![\w.])` guard could never have matched one anyway.

- **The turbulence modules' version labels are measured too** — v1.12.0 corrected the blanket Foundation v13 tag across the core schemas and `snappyHexMeshDict`, but noted that the same understatement survived in the two foamlore-generated turbulence modules: a Foundation v10 user selecting `beta1` in `constant/momentumTransport` was still told "Foundation v13", and an OpenCFD v2106 user was told "OpenCFD v2512, v2606". Those are vendored generated files, so the correction was recorded in the generator's spec rather than hand-edited here — and it has now been made there. foamlore widened its own source coverage from four checkouts to all seventeen releases either fork has a version constant for, re-extracted every coefficient across all of them, and regenerated: the 111 entries in `momentum_transport.py` now read `Foundation v8-v13`, which is every release that reads that file name, and the 109 shared entries in `turbulence_properties.py` read `OpenCFD v2106-v2606`. The Foundation tag on `turbulence_properties.py` stays at v7 alone, which was already right — v8 is where the file was renamed. Two new labels in `schemas/_base.py` carry the ranges that are neither a single release nor a whole fork: `FOUNDATION_V8_V13` and `OPENCFD_V2212_V2606`.

  Measuring every release rather than sampling also corrected two things this repository's own audit had got wrong, both from releases the sample skipped. The SpalartAllmaras `ft2` term — `ft2`, `Ct3`, `Ct4` and `ck` — arrived in **v2212**, not v2306. And `sigmaNut`'s source default changed at v2212 from `scalar(2)/scalar(3)` to the literal `0.66666`, a real if small numeric difference that was invisible from the four checkouts previously on disk, since v2512 and v2606 both carry the newer spelling. Both defaults are now offered as choices with their own version tags.

### Documentation

- **An eighth demo movie: what the model is, not just its name** (`pitzDaily-turbulence-notes`, ~64 s) — the two entries above are the hardest thing in this release to show in a still, because the argument is not that there is a note but that there is a *different* one for every value. So it is a movie: `constant/turbulenceProperties` open on the bundled pitzDaily, the `RASModel` row selected, and the Choices box walked down its list while the Choice Help, Choice Supported In and Choice Note rows rewrite underneath it — kEpsilon with Launder and Spalding, kOmegaSST with a blank note because its header cites no paper, SpalartAllmaras with three, then eleven presses down to `laminar`, the one row in the list FoDE writes itself. The closing frame is the point: the tree still reads `kEpsilon` and the file is not dirty, because the pane updates its help from the combo box and writes the node only on **Apply Value**. Scripted in `tools/demo_specs.json` and driven by `tools/demo_driver.py` like the other seven, so a retake is one command; the shot-by-shot script is in `docs/DEMO_SCRIPTS.md`.

- **A bundled case that is actually turbulent** (`tutorials/pitzDaily/`) — every case in `tutorials/` was laminar: `damBreak` and both regions of `snappyMultiRegionHeater` say `simulationType laminar`, and the rest have no turbulence dictionary at all. Two releases of turbulence-model help therefore had nothing bundled to try it on, and neither did anyone reading about it. `pitzDaily` is the canonical RAS tutorial — `simpleFoam`, `kEpsilon`, a backward-facing step that meshes in a second — and is redistributed unmodified from the OpenFOAM v2512 tutorial set, under the GPL-3.0 that covers the rest of `tutorials/`. Open `constant/turbulenceProperties` in it and the model selector, its choice descriptions and the whole coefficient table are in front of you; `system/streamlines`, reached through the `#includeFunc` in its `controlDict`, is a working example of the include machinery besides.

## v1.12.0 — 2026-08-05

### New features

- **Turbulence-model coefficient help in the Detail pane** — two new schema modules, generated from the OpenFOAM source code by the sibling foamlore project and enabled by default, cover `constant/turbulenceProperties` (OpenCFD v2512/v2606, Foundation v7) and `constant/momentumTransport` (Foundation v13, the file's post-OpenFOAM-8 name). Clicking a coefficient of `kOmegaSST`, `kEpsilon`, or `SpalartAllmaras` — whether inside a `<model>Coeffs` sub-dictionary or directly in the `RAS` dictionary — shows which fork/versions define it and its source default as an applicable choice, extracted mechanically from each version's `.C` constructor (e.g. `beta1` = 0.075, `Cmu` = 0.09, including OpenCFD-only additions such as `decayControl`, marked as such). Existing installations with a customised schema module list can add `schemas/turbulence_properties.py` and `schemas/momentum_transport.py` via **Settings > Manage Schema Modules > Add Module from File**.

- **Schema help now covers the dictionaries it names** — the six built-in schemas were shallow, and one was unreachable. Measured against every matching dictionary in the OpenFOAM v2606 tutorials, the share of entries that get help has gone from 0% to 99% for `fvSchemes`, 28% to 97% for `fvSolution`, 40% to 97% for `controlDict`, 5% to 85% for `blockMeshDict`, 58% to 98% for `snappyHexMeshDict`, and 3% to 96% for `turbulenceProperties`. The keys people click first — `divSchemes`, `solvers`, `PIMPLE`, `vertices`, `blocks`, `castellatedMeshControls` — had no entry at all and now do, and the value dropdowns list what OpenFOAM actually registers, so `tolerance`, `relTol`, `endTime`, `deltaT` and the whole `divSchemes` category are documented for the first time.

- **Entries named after your case are now recognised** — a schema can declare a wildcard for a dictionary whose children are named after the case's own fields and patches, so `div(phi,U)`, `solvers { p { … } }` and `relaxationFactors { equations { U 0.7; } }` get help without every possible name being listed in advance.

- **Turbulence structure, not just coefficients** — a new schema covers `simulationType`, the `RAS`/`LES`/`laminar` dictionaries, the `model` selector with the full model list for each fork, and the LES delta models. It applies to `constant/turbulenceProperties` and `constant/momentumTransport` alike, since a schema module can now name more than one target file and several modules can contribute to the same dictionary.

- **The Detail pane says when a key is old, or does nothing** — a key that OpenFOAM renamed is kept and labelled with its successor and the version that changed it, rather than being presented as current. A key that appears in the official tutorials but that no OpenFOAM reader consumes is flagged in warning colour with the key that is actually read. The first case of each: `minMedianAxisAngle`, renamed to `minMedialAxisAngle` in v1712 and still accepted by Foundation but dropped by OpenCFD in v2212; and `minFlatness`, which the motorBike tutorial has shipped in both forks since OpenFOAM-2.3.x while OpenFOAM reads `minFaceFlatness` and silently ignores it.

### Bug fixes

- **Schema help for `fvSchemes` never appeared at all** — the module wrote its keys the opposite way round from the way they were looked up, so every one of its entries was unreachable: selecting `ddtSchemes/default` offered no description and no list of schemes, in every case, since the module was written. Its unit tests passed because they asserted the internal table shape rather than the call the Detail pane makes. The keys are corrected, and a new test parses real tutorial dictionaries and walks them the way the pane does, so a module cannot go dark again without the build failing.

- **New built-in schemas reach existing installations** — the saved schema module list was authoritative, so anyone who had opened **Settings > Manage Schema Modules** even once was pinned to the modules that existed that day and never received a later one. The built-in defaults are now merged into the saved list on every load, and only modules you explicitly removed stay out. If you removed one before this release there was no record of the intent, so it will reappear once and can be removed again.

- **`blockMeshDict`'s `mergeType` no longer offers an invalid value** — the dropdown listed `merge`, which OpenFOAM does not accept, and omitted the real default `topology`; the two descriptions were also swapped. Choosing from the list produced a dictionary blockMesh could not read as intended.

- **Version labels no longer claim shared keys are Foundation-only** — 61 entries, including all of `fvSchemes` and most of `fvSolution`, were tagged as Foundation v13 despite belonging to the `finiteVolume` and `lduMatrix` libraries that both forks share, telling OpenCFD users that core keys were unavailable to them.

- **A sub-dictionary's schema help no longer borrows another's keys** — the Detail pane resolves a key by looking first for it under the surrounding dictionary's name and then, failing that, for a plain entry of the same name. The second step had no sense of where it was: a key written inside one named sub-dictionary could be answered by an entry that belongs to a different one, described confidently and offered with a default value that does not apply there. A dotted prefix is now a closed namespace — once a schema module qualifies any key under a name, a key it does not qualify there is not that dictionary's key, and the flat fallback stays quiet instead of guessing. Keys that no namespace claims are untouched and still fall back from anywhere, which is what keeps the flat spelling of a dictionary that OpenFOAM reads through `optionalSubDict` working, and what leaves every `snappyHexMeshDict` lookup exactly as it was — none of its nine sub-dictionaries has a key with a flat twin, so the rule cannot fire there at all. The saving is not that the pane says less: it is that it stops attributing one thing's meaning to another, which a reader has no way to catch from the pane itself.

- **`constant/regionProperties` now opens as a proper entry** — the file that names a multi-region case's regions used to be the one file about that case you could not read in the tree. `regions ( fluid (bottomAir topAir) solid (heater leftSolid rightSolid) );` came out as two nameless amber rows, one holding the bare word `regions` and the other the whole parenthesised body, because the `regions` key was routed unconditionally to the named-dictionary parse that `setFieldsDict` needs (`regions ( boxToCell { … } );`) and anything not in that shape was treated as a failure. The key is now decided by the same lookahead `sets` and `surfaces` already use: named dictionaries still parse to `region_block`/`region_entry`, so the setFields overlay is unchanged, and everything else falls through to the ordinary list handling — exactly what an identically shaped entry under any other key already produced. Across the v2512 tutorials this takes the number of `regions`-bearing files reporting a parse error from 45 to 24, with no change to the 135 files that parse as a `region_block` and no difference to any file's byte-for-byte round trip.

- **Most of the tutorial dictionaries that failed to parse now open** — three defects in the value reader accounted for the bulk of every parse failure across the 4435 dictionary files in the v2606 tutorials: 288 files reporting 861 errors are now 38 files reporting 217. The first was a dictionary written inside an entry's value, as `fvSchemes` does in `div(phi,Yi_h) Gauss multivariateSelection { O2 limitedLinear01 1; … };` — the reader tracked brace depth but had no case for a `;` inside the braces, so the entry degraded to a nameless amber row, the block's own entries were stranded as siblings of the dictionary that should have contained them, and the closing `};` then ended `divSchemes` early, leaving every later `div(...)` parsed as a top-level node. The tree showed a structure the file does not have. The second was an entry with no value at all — `fluxRequired { p; pcorr; }`, `cache { grad(U); }` — where the key carries the whole meaning; each came out as a nameless raw row that had lost the field name that was its entire content, and schema help had no name to look up. Those are now a `valueless` node type: the key stays editable, the Value column is not, because there is nothing there to edit. The third was a comment between a key and its opening brace, which `thermophysicalProperties` writes as `mixture // air at room temperature (293 K)` on the line above the `{`; the comment is now kept and written back on the key's line, where the source had it. Round-trip fidelity is unchanged throughout — all 4435 files still write back byte-identical — because a failed entry was always preserved verbatim; what these fix is what you can see and click, not what lands on disk. The 217 errors that remain are four causes with clear shapes rather than a long tail, and each is recorded in `DEVELOPER.md` with the trade-off that has so far kept it open.

- **`snappyHexMeshDict`'s version labels are measured rather than assumed** — the correction above for 61 core entries left the snappy package still carrying the same blanket Foundation v13 tag, so selecting `snap` reported "Foundation v13, OpenCFD v2106-v2606" for a key that has existed since at least v7, which reads as "not available to you". Rather than swap one guess for another, every one of the 107 key names the package documents was checked against the sources themselves — Foundation 7 through dev, OpenCFD v2106 through v2606 — and 97 are present in Foundation v7 already, which is what the tags now say. The scan also found the genuinely fork-specific keys, now recorded as measured: `minEdgeLength` (OpenCFD v2306 and later, in no Foundation release), `thicknessModel` and `nSmoothInternal` (OpenCFD only), `radius1`/`radius2` (Foundation from v12), and `minMedianAxisAngle` (Foundation v7-v13, but only OpenCFD v2106/v2206). One entry, `appendRegionName`, had no basis in either fork or in any tutorial and is removed; the `yes`/`no` switch choices were tagged Foundation-only though `Switch` accepts them in both forks, and `on`/`off` were missing altogether. The same understatement survives in the two foamlore-generated turbulence modules — a Foundation v10 user selecting `beta1` is still told "Foundation v13" — but those are vendored generated files, so the correction is recorded in the generator's spec rather than hand-edited into them.

### Documentation

- **A seventh demo movie: the paper's worked example, end to end** (`cavity-full-workflow`) — the six movies above each answer one question in under 75 seconds. This one answers the question they leave out, which is what a whole case looks like from one end to the other, and takes three and a half minutes to do it. It is Appendix A of the SoftwareX paper — the lid-driven cavity solved with `icoFoam` — recorded beat for beat: the window opens with no case at all, duplicates `cavity` out of the case library, walks the file list and the `[+]` marker that reveals `PDRblockMeshDict`, reads `controlDict` in the tree with the schema-driven detail panel open on `writeControl`, gathers the boundary conditions into the Boundary tab and follows a cell back to the line it came from in `0/U`, runs `blockMesh` and then `icoFoam` in the embedded terminal while the file list grows a mesh row and five time directories, condenses both logs through **View Log Summary…**, and ends in ParaView with the velocity field at 0.5 s — which is Fig. A.6 of the appendix, on screen rather than described. A reader who has just finished the appendix can watch it happen instead of imagining it. Recording it needed three things the driver did not have: a scratch `app_config.json` per take, so that duplicating a case no longer writes the recording machine's settings and so that the feature flags and case library a movie opens with are the same on every machine; a `case_library` scene key, so the case chooser always opens on the same staged tutorial tree rather than on whatever the recording shell had registered; and targets for a file-list group header, a form field named by its label, and a boundary-table cell named by its two headers. It is also the first scene to drive an application that is not FoDE, which ParaView pays for in pixel coordinates rather than names.

- **Six demo movies, and the scripts they were shot from** (`docs/DEMO_SCRIPTS.md` / `docs/DEMO_SCRIPTS_ja.md`) — short walkthroughs published on YouTube and linked from `README.md`, covering the edit-see-run loop on `damBreak`, the `topoSetDict` overlay on `topoSetShapes`, the boundary table and case comparison on `cavity`, `snappyHexMeshDict` on `motorBike`, sampling merged from three files on `samplingShapes`, and the per-region file grouping on `snappyMultiRegionHeater`. The document is a shot-by-shot script for each: what is on screen at every beat, the narration that goes with it, and why the beat is framed the way it is. Five of the six use cases bundled in this repository, so anyone with a checkout can replay what the movie shows. What makes the scripts worth keeping is that they are not prose *about* the movies but the movies themselves: each is a scene in `tools/demo_specs.json` that `tools/demo_driver.py` plays and records, starting from the same `ui/window_state.py` window state the screenshot gallery uses and then driving the window with real mouse and keyboard input. A retake is one command, which is what stops a demo going stale the way a hand-recorded one does — and `tests/tools/test_demo_specs.py` checks the scenes against the UI, so a renamed menu item fails in the test suite rather than halfway through a recording. The videos themselves are deliberately not tracked: they regenerate from the spec, and video does not delta-compress, so every retake would sit in history forever. The `.srt` caption files beside them are tracked, being a few kilobytes of text and the track to upload alongside each video.

## v1.11.0 — 2026-07-31

### New features

- **FoDE reopens where you left it** — closing the application now records the shape of the window and what was in it, and the next launch puts that back: window size and position, the splitter positions, the active upper and lower tabs, the Terminal's mode, the case directory and every file that was open in it, which file was on screen, the selected tree row, and the BlockMesh panel's toggles, label size and camera angle. The 3-D view in particular comes back at the angle you left it rather than the default one, which previously meant re-orienting the same case by hand at the start of every session. What is *not* restored is anything the window works out for itself — scroll positions, the editor's cursor and folded regions, tree expansion beyond the selected row's ancestors — and unsaved edits, which are still settled by the usual dialog when you close. Nothing about a saved session can stop the application opening: a case that has been renamed, a file that has been deleted, a tree row that no longer exists or a layout written by a later version of FoDE is skipped part by part, the rest is restored, and a line in the status bar names what was left out. A large non-dictionary file such as a `log.*` run log is deliberately among the things left out: opening one asks for confirmation because it freezes the window while it loads, and neither asking that at startup nor answering it on your behalf is right. **Settings > Restore Last Session on Startup** is ticked by default; unticking it opens a default window next time and *keeps* what is stored, so re-ticking returns you to the same layout. Throwing one away is **Settings > Forget Saved Session**, which discards every variant's stored layout and greys itself out when there is nothing left to forget — a checkbox that says one thing should not quietly do the other, and the case paths a layout records are worth being able to clear on purpose. `python3 main.py --no-restore` skips the restore for one launch without touching the setting or the stored session. Each `--variant` keeps its own layout, since variants change which panels and tabs exist.

- **`--theme` on the command line** — `python3 main.py --theme dark` launches in a colour theme for that run only, leaving the saved **Settings > Appearance** setting untouched. The theme setting has always needed a restart to take effect, which made comparing the two a matter of changing the setting, restarting, and changing it back; now two windows in different themes can sit side by side, and neither of them decides what the next launch looks like. `system`, `light` and `dark` are all accepted, the same three choices the Appearance menu offers. Without the flag nothing changes: the saved setting is used exactly as before.

- **A new bundled example case, `tutorials/samplingShapes`** — the sampling counterpart of `topoSetShapes`, which has done the same job for `topoSetDict` since it was added. Sampling is the awkward one of the four overlays to see working: it has no dictionary of its own, being writable as a function object inside `controlDict` or as a standalone dictionary, and the standalone form accepts two different member-list syntaxes. Nothing in the OpenFOAM tutorials exercises more than a fraction of that — across the whole v2512 and v2606 tutorial sets, only two cases define a sampling plane at all, and none combines one with probes and lines. This case puts all of it in one 3×3×3 block: probe points, a span-based line, a point cloud, and both plane spellings, spread across a `controlDict` `functions {}` block and two standalone dictionaries written in the two different syntaxes, plus a non-geometric `patch` surface and a non-sampling function object so the difference between "listed without geometry" and "ignored entirely" is visible too. The shapes are deliberately placed apart rather than tidily: each shape's name badge is drawn at that shape's own centre, so a case with everything at the middle stacks its badges into an unreadable pile.

### Bug fixes

- **The clipped-shape mark in the 3-D viewer is visible again** — an overlay shape too large for the block mesh is drawn cut down to it, and its name badge carries a mark so the cut is not mistaken for the shape's real extent. That mark was `✂ clipped`, and the scissors reached the screen as nothing at all: these labels are drawn by VTK rather than Qt, and VTK's built-in label font has no glyph for it, so it drew no glyph — not even a placeholder box — while the badge still reserved the width. What you saw was `midPlane   clipped` with an unexplained gap in it. The marks are now `(clipped)` and `(outside block mesh)`, in plain ASCII and parenthesised the same way the overlay menus' own `(no geometry)` rows are. Square brackets turned out to be no good either — VTK's font renders them as parentheses — which is worth knowing before putting any symbol in a 3-D label.

- **The 3-D viewer's X/Y/Z extents readout shows what separates its two numbers** — the same missing-glyph problem, in a second place. The **Dimensions** overlay writes each axis as `X  -5 → 15  (20 m)`, and the arrow was drawn as nothing, so the readout arrived as `X  -5   15  (20 m)`: two numbers with an unexplained gap between them, and no indication that they were the ends of a range rather than, say, a value and a count. It now reads `X  -5 .. 15  (20 m)`. A hyphen would have been the obvious choice and is the wrong one, since a range starting at a negative number would read as `-5 - 15`.

- **The 3-D viewer's orientation axes are legible in the dark theme** — the small X/Y/Z triad in the bottom-left corner of the BlockMesh viewport was the one part of the 3-D scene that ignored the colour theme. Its letters were left at PyVista's default black in all three modes, so against the dark theme's `#2E3238` viewport background they were all but invisible. They now take the same colour as the bounds readout above them, which was already themed. The axis arrows keep their conventional red/green/blue in both themes — those identify the axes rather than decorate them, the same rule the patch and overlay colours follow.

- **The 3-D grid's tick labels no longer read as faintly as the gridlines they sit on** — the grid's numbers and axis titles were drawn in whatever colour the gridlines were given, because VTK's `show_grid` paints lines and text from a single value. That colour is deliberately faint, which is right for a gridline and wrong for a number you are meant to read: on the light theme's white viewport it left them at 3.95:1, below the 4.5:1 a body of text wants. The two are now separate settings, so the lines stay exactly as faint as before while the text moves to 7.5:1 on the light theme and 7.7:1 on the dark one. Dark mode was already adequate at 4.58:1, so this was a light-theme problem that the dark-theme work happened to surface. The colour table's own legibility test is what let it through: it held every viewport colour to 3.0:1, which is the right target for lines and the wrong one for text. It now checks text at 4.5:1 and leaves the gridlines at 3.0:1.

- **An overlay shape cut down to the block mesh is no longer hollow** — a shape mesh is a hollow surface, and the cut left it open, so a shape with both of its end caps outside the clip box came back a tube with nothing inside. That is the ordinary case rather than a corner one: a `setFieldsDict` region is conventionally written to span the whole depth of a quasi-2-D case — damBreak's `box (0 0 -1) (0.1461 0.292 1)` against a tank 0.0146 m deep — and the front view is the one angle such a case is ever looked at from, so the initial water column appeared as an empty orange outline drawn over the mesh rather than as a filled region. Each cut is now sealed and a clipped shape reads as a solid, the same way an unclipped one always has. Cylinders gain the most: their seam carries duplicate points that made them fail the closed-surface test outright, and merging those points first is what allows them to be capped at all. Shapes with no volume to seal — a `planeToFaceZone` plane, a sampling disc — keep exactly the behaviour they had. Nothing about what the clip *means* changed: the dictionary and the extracted geometry are untouched as before, and **Export Shapes as STL…** still writes the full shape.

- **Reset All Settings now actually resets the application settings** — the dialog deleted `app_config.json` and said so, but the application went on running, and closing the window wrote the file straight back: the shut-down captures the session layout and the window size, so the settings the reset had just removed came back with the next launch. The saved session was the visible half of this — resetting the settings and reopening FoDE put you back in the same case, in the same layout, which is the opposite of what was asked for — but every key in the file was affected in the same way, `window_size` included. The deletion now holds: once the application settings have been reset, closing the window persists nothing, so the next launch starts from the defaults. That is what the dialog's "please restart the application" has always meant, and the completion message now says what it costs, namely that the layout and size of that session are not saved. Settings you go on to change deliberately after the reset — picking a theme, say — are still saved as before; only the automatic capture on the way out is suppressed. Resetting the schema settings is unaffected, since `schema_config.json` has never been written at shut-down.

- **The Reset Settings dialog no longer describes settings that do not exist** — the tooltip on **Application Settings (app_config.json)** read "Reset case directory, window size, and recent cases". There is no recent-cases feature, and the file has since grown to hold the theme, the language, the case library, your links, the OpenFOAM installation directory and the saved session, none of which were mentioned — the saved session least excusably, since that is the part of a reset people notice. The tooltip now lists what is actually reset. The confirmation dialog's text, which was assembled from untranslated English fragments while its Japanese translations sat unused in `i18n/ja.py`, is now translated too.

## v1.10.0 — 2026-07-30

### New features

- **Files pulled in by `#include` are now listed and readable** — a dictionary that says `#include "caseSettings"` or `#includeEtc "caseDicts/setConstraintTypes"` used to leave FoDE with nothing to show: the directive was stored as opaque text and the file it named was invisible, even though understanding the case often depends on reading it. Those directives are now resolved and the files they refer to appear in the file list, marked `↳`. An include landing inside the case joins the group it belongs to, so `constant/caseSettings` shows up under **constant** and is editable like anything else. One that resolves into your OpenFOAM installation — which is where roughly half of them go, `#includeEtc` alone accounting for 560 of the 1,081 directives in the v2512 tutorials — is collected in a new **included files** group at the bottom, in italic, with a tooltip naming the file that included it. Nothing is merged into the including dictionary: the included file stays a file of its own, the way a symlinked file does, and the directive keeps its own tree row. Right-clicking that row offers **Open Included File** (double-clicking its Key or Type cell does the same), and hovering it reports what the directive resolved to — or that the target is missing, that an optional `#sinclude` is simply absent, or that no OpenFOAM installation was found to resolve `#includeEtc`/`#includeFunc` against. All five directive forms are handled, including `<case>`/`<system>`/`<constant>`/`<etc>` path tokens, `$FOAM_*` variables, and `#includeFunc mag(U)`-style arguments; 1,072 of the 1,081 directives in the v2512 tutorials resolve, the remaining nine being files that `Allrun` generates and that genuinely do not exist yet in a pristine case. Includes are followed one level only, and a C++ header included inside a `#codeStream` body is deliberately ignored rather than offered as a dictionary.

- **Files from the OpenFOAM installation are read-only, with a one-click way to make them yours** — an `#includeEtc` target lives inside your OpenFOAM installation and is shared by every case on the machine, so editing it in place would be a mistake that is hard to notice and harder to undo. Such files open normally — full tree, full text, syntax highlighting — but the editor is locked and shows a `read-only` badge, tree entries cannot be edited, and Save, Save All, Create Backup, Duplicate and Delete are all unavailable rather than silently writing where they should not. **Copy into case...** on the file's context menu is the way through: it copies the file into your case, defaulting to `system/`, which is exactly where OpenFOAM looks before consulting its own `etc/` — so for `#includeFunc` the copy takes effect with no edit to the directive at all. The copy is a normal, editable case file and is registered in the file list so it survives later changes to the directive. Unsaved edits in other open files are preserved across the copy.

- **`blockMeshDict`'s blocks now appear one per row in the Tree view** — the `blocks ( … );` entry used to arrive as a single row holding every block as one long string (five blocks and roughly 380 characters, in the `pitzDaily` tutorial), even though the BlockMesh 3-D viewer had always drawn them as separate, individually coloured and numbered blocks. It now expands to `block 0`, `block 1`, … in the same order and with the same numbers the viewer draws at each block's centre, so the two views finally refer to the same thing. Each row is editable on its own and hovering shows a breakdown of the block's vertices, cell counts, grading, and zone; clicking a row scrolls the Editor tab to that block rather than to the top of the list. Round-trip fidelity improves as a side effect: editing one block used to reflow the entire list onto a single line, and now leaves every other block byte-for-byte as it was. Lists that aren't a plain sequence of `hex` blocks — an empty list, or one built from macros — keep their previous single-row behaviour, so nothing that parsed before parses differently now. A list that mixes an `#include` in with its blocks does expand: the directive gets a row of its own among the blocks, and the block numbering steps over it so it still starts at 0 and still matches the viewer. One consequence worth knowing: in compare mode, blocks are matched by position, so a file where two of five blocks differ is now marked `≠2` where it previously showed `≠1`.

- **Blocks can be added, duplicated and deleted from the Tree view, and the selected one is highlighted in 3-D** — the two things left over from showing `blockMeshDict`'s blocks one per row. Right-clicking a `block N` row now offers **Add Entry After**, **Duplicate** and **Delete** like any other entry; a newly added row starts as a real `hex (0 1 2 3 4 5 6 7) (10 10 10) simpleGrading (1 1 1)` block rather than an empty placeholder, so it survives the next **Apply Text to Tree**, and deleting one renumbers the rows after it automatically. Selecting a block row outlines that block in the BlockMesh 3-D viewer, which works because the row number and the number the viewer draws at each block's centre are the same number — the outline shows even with **Block edges** and **Solid blocks** both switched off, and clears when you select anything else. **Comment Out** stays unavailable on block rows: a commented-out block inside `blocks ( … )` reads back as a comment rather than an entry, so the row would disappear instead of being restorable.

- **Colour theme setting (Settings > Appearance)** — a new **Follow System** / **Light** / **Dark** choice, saved in `app_config.json` and applied on restart. **Follow System** (the default) keeps the platform's native widget style and desktop palette; **Light** and **Dark** force the Fusion style with FoDE's own palette so the window looks identical on every OS. Dark mode retunes the whole UI, including the editor's syntax highlighting, the line-number gutter, diff row backgrounds, the notice banners, and the BlockMesh 3-D viewer — whose scene background, axis/bounds text, vertex and block labels, and shape name badges follow the theme too, instead of the viewer staying a fixed white rectangle inside a dark window. Every colour the UI draws now resolves through one table in the new `ui/theme.py` instead of being hard-coded across a dozen files, so the two themes cannot drift apart — the diff legend swatches and the tree's diff row backgrounds, for instance, now read the same values by construction.

- **The BlockMesh 3-D panel's Load STL / OBJ dialog now accepts several files at once** — the viewer has always been able to show any number of STL/OBJ overlays, but the file chooser only let you pick one per visit, so a snappyHexMesh case with a folder full of surfaces in `constant/triSurface/` meant reopening **STL ▾ > Load STL / OBJ…** once per file. The dialog now allows a multi-file selection and loads everything chosen in one pass, still adding to whatever is already on screen. If one of the selected files can't be read, the others are still loaded and a single warning names the ones that failed, instead of the first bad file ending the whole load.

- **Each loaded STL/OBJ surface now has its own row in the `STL ▾` menu** — the viewer kept loaded surfaces as anonymous meshes and threw away the path each came from, so once several were on screen there was no way to tell what was loaded, hide one, or remove one: **Clear STL** dropped all of them or nothing. Every file now gets a checkable row listing its name, in its own colour from a pale palette so surfaces stay apart in the 3-D view, alongside a **Show loaded surfaces** master toggle and **Show all surfaces** / **Hide all surfaces** — the same arrangement the topoSet, snappyHexMesh, setFields and sample menus have always had. An **Unload ▸** submenu removes a single file, and loading a file that is already loaded re-reads it into its existing row instead of stacking a duplicate, which makes it the way to refresh a surface edited outside FoDE. A surface loaded on its own, with no `blockMeshDict` open, is also drawn now — it used to be loaded and listed but never rendered, because the viewer skipped drawing entirely when there was no mesh or dictionary overlay to show.

### Bug fixes

- **Dictionaries using `${...}` macro references, or a macro without a trailing semicolon, now parse** — two spellings OpenFOAM accepts had never been understood, and either one turned a whole file into a "Text was loaded, but tree update failed" warning with an empty tree. The first is a braced macro reference, which may carry a scope path: `${../_bladeForces};` in `propeller1/system/bladeForces`, `${__settings}` in the `gasMixing` sampling dictionaries. FoDE's lexer ended a word at the `{`, so a bare `$` was left standing as an entry key and the parser then failed demanding a `;`. The second is a macro used as a complete statement with no terminator at all — `maxX { $minX }` in several `pointDisplacement` files, `"pcorr.*" { $p … }` in four `pimpleFoam` `fvSolution` files — which the parser required a `;` after. Between them these accounted for **every** remaining parse failure across the OpenFOAM v2512 tutorials: measured with `tools/roundtrip_corpus.py` over the 9620 files under `system/`, `constant/`, `0/` and `0.orig/`, 9501 parsed before and all 9620 do now, with the byte-identical round-trip rate staying at 100%. The 119 files affected are not obscure — they include `system/snappyHexMeshDict` in four mesh tutorials, `createBafflesDict`, `fvSolution`, and the header-less sampling fragments in `system/` (`sampling`, `fieldTransfer`, `avg-tracer0`). Because the `;` is genuinely optional it is no longer stored as part of the entry, and the writer reproduces whichever form the file used, so editing a bare `$p` no longer silently adds a semicolon it never had.

- **Saving a file no longer rewrites blank lines you never touched** — opening a tutorial case and hitting Save reformatted the file even with no edits made: the blank line after the `// * * *` header banner moved to above it, gaps of two or more blank lines between entries collapsed, several entries written on one line (`x1 14; x2 6;`) were exploded onto separate lines, and the closing `// ****` footer banner was deleted outright. This affected every one of the 439 parseable `system/blockMeshDict` files in the OpenFOAM v2512 tutorials. Measured across the tutorials as a whole — every file under `system/`, `constant/`, `0/` and `0.orig/`, of which 9501 parsed at the time of this fix (the macro-entry fix below later took that to all 9620) — 286 saved back byte-for-byte identical before this release, and every parseable file does now. `tools/roundtrip_corpus.py` is that measurement, so the figure can be re-run against any installation rather than taken on trust. The cause was the writer adding a line break that the parser had already recorded as belonging to the next entry, plus two blunt regular expressions that tried to undo the doubling and removed real blank lines with it; the footer banner, which follows the last entry and so belongs to no entry, was simply discarded at parse time. Saving an edited file now rewrites only the entries actually edited, and a file that ended without a final newline keeps ending without one.

- **A dictionary written `divSchemes { … };` no longer moves its semicolon to a line of its own** — a `;` after a closing `}` is redundant but legal. FoDE parsed it as a separate entry, reported it in the status bar as an unrecognised entry, and on save pushed it onto the next line. This was the sole remaining reason a file changed on save without being edited — 54 dictionaries in the v2512 tutorials, mostly `fvSchemes`, which is what closed the gap to all 9501 then parseable. The `;` is still its own entry — it is real text and has to be written back — but it is no longer counted as a parse failure, and the writer now keeps an entry that touched the previous one in the source on that same line instead of assuming it needs a fresh one.

- **Editing an entry inside a block no longer shifts it to the right** — an edited entry that sits inside a dictionary was rewritten with its indentation doubled: change `nCorrectors` inside `PIMPLE { … }` and it moved from four spaces to eight, and the deeper the nesting the further it drifted. This hit the first line of every kind of nested entry — a plain `key value;`, a sub-dictionary's name, an `#includeFunc` directive, a `$macro`, a `regions`/`actions` entry, a `fieldValues` block — so any tree edit or **Use this value** on a nested key left a visibly misaligned line behind. The writer was prepending its own indentation on top of the indentation it had already reproduced from the source. Individual blocks in `blocks ( … )` were the one case that had been compensated for, which is why this went unnoticed.

- **Case Library dialog module no longer fails to import on Python 3.10/3.11** — `ui/dialogs/case_library_dialog.py` used an f-string that reused the same quote character for its outer and inner (nested `tr(...)`) string literals, which is a Python 3.12-only syntax relaxation and raised a `SyntaxError` on 3.10/3.11 as soon as the module was imported (i.e. on first opening **Case > Manage Case Library…**). The nested string now uses single quotes so the file parses on all supported Python versions.

- **The Detail panel now shows the value of a selected field entry** — selecting a `field_value` row (e.g. a `value uniform (0 0 0)` entry inside a `0/` field file's `boundaryField`) called a formatting method that no longer exists on the tree model, raising an `AttributeError` inside the Qt slot: the app kept running, but the Detail panel's value box stayed empty and a traceback was printed to the console. The panel now calls the actual formatter in `foam/utils.py`. Found by extending the type-checker to `ui/`.

- **Case > Duplicate Case… again pre-fills the destination folder** — the dialog was constructed with the main window passed positionally where the default destination-parent string was expected, so Qt treated it as a widget parent for the text field: the destination-parent box opened empty instead of pre-filled with the case's parent directory, and the dialog itself was unparented. Found by extending the type-checker to `ui/`.

- **STL/OBJ overlays no longer follow you into the next case** — surfaces loaded into the BlockMesh 3-D viewer through **STL ▾ > Load STL / OBJ…** stayed loaded when you opened a different case, so geometry belonging to the case you left was redrawn over the new one's mesh, and **Clear STL** was the only way to get rid of it. Opening a case already reset everything else the panel shows — the topoSet/snappyHexMesh/setFields/sample overlays and their menus, the vertex table, the 3-D scene — and it now clears the loaded surfaces along with them.

- **Selected rows are no longer unreadable on Windows 11** — Qt takes the selection fill from the desktop (on Windows, the accent colour from *Settings > Personalization > Colors*) but takes the selected-row text colour from the system palette independently, and nothing checks that the two work together. On Windows 11 this rendered near-black text on a saturated blue selection in the tree and file list. FoDE now recomputes the pair itself in all three theme modes. Note that the obvious fix — pick whichever of black or white has more contrast — reproduces the bug rather than fixing it: the default Windows 11 accent `#0078d4` scores 4.64:1 against black and only 4.53:1 against white, so black wins on the numbers while still being the combination that is hard to read. The rule applied instead follows what desktops actually do: white text whenever it reads adequately on the fill, dark text only on a genuinely light fill (a yellow or pastel accent), and otherwise the fill is darkened slightly — keeping its hue, so the user's accent colour stays recognisable — until white clears. Linux and macOS were unaffected but go through the same path.

- **A `#include` among the blocks no longer collapses them into a single row** — the same `blockMeshDict` that pulls patches in from another file does it for blocks too (`blocks ( #include "blockMeshDict.caseBlocks" hex … );`), and the directive made the whole list fall back to one long unexpandable row, so none of the 24 blocks written in the file could be selected, edited or highlighted individually even though the 3-D viewer drew all of them. The directive now takes a row of its own among the block rows. Its own contents stay invisible — in the tutorial case it is a symlink `Allrun` creates at run time, pointing at one of two alternative block files, so there is nothing to read at edit time — which means the numbering counts the blocks written in this file only, exactly as the 3-D viewer already did. That is what keeps `block 0` in the tree and the `0` drawn in the viewer the same block; both can differ from blockMesh's own numbering once it resolves the include.

- **A `#include` among the patches no longer costs a `blockMeshDict` its boundary** — a boundary block that pulls part of its patches in from another file, as `boundary ( #include "blockMeshDict.caseBoundary" outlet { … } );` does, failed to parse as a boundary: the whole block fell back to raw text, was reported as two unrecognised entries, and lost its editable patch rows in the Tree view. The 3-D viewer then drew it wrongly rather than not at all — the fallback text scanner read `include` as a patch name and handed it the *next* patch's faces, so in the one v2512 tutorial written this way (`compressible/rhoPimpleFoam/laminar/helmholtzResonance`) the `outlet` patch disappeared from the viewer and a phantom patch named `include` took its 9 faces. The directive is now parsed as an entry in its own right, sitting among the patches, so everything around it keeps its structured parse: the tutorial above now reports no parse errors and shows `outlet` (patch) and `sides` (symmetry) with the right faces. Files that use `#include` this way still save back byte-for-byte identical, and the round-trip figure above is unchanged.

- **Two sampling dictionaries with the same filename no longer hide each other in the 3-D viewer** — the `sample ▾` overlay tracked its loaded files by filename alone, so if a second dictionary with the same basename came into view — reachable by adding an extra directory that holds its own `sample`, `probes` or `surfaces` — the newer one silently replaced the older one's shapes in the menu, and the remaining rows named the wrong source file. Files are now tracked by their full path, while the menu rows still show just the filename.

- The newer OpenFOAM compact boundary face notation — `(blockIndex faceIndex)` — is now supported alongside the traditional 4-vertex notation `(v0 v1 v2 v3)`.
- The compact form is expanded to a 4-vertex list using the standard hex block face table (face 0 = −x, 1 = +x, 2 = −y, 3 = +y, 4 = −z, 5 = +z). Both notations can coexist in the same file.
- Previously, compact face entries were silently dropped (the `len < 3` guard rejected 2-integer tuples), so boundary patches using the new notation were invisible in the 3-D view.

- Added a **Reload Case** button to the top bar, placed between **Save All Files** and the separator. The button is equivalent to **Case > Reload Case** and provides one-click access to the most common case-reload operation.

The running-state indicator (menu item text changes to **■ foamMonitor**) and stop-by-click behaviour are unchanged.

### Bug fixes

- **BlockMesh viewer: negated-macro vertex variables now resolved** — Variable definitions of the form `xMin -$xMax;` (a leading minus sign before a `$reference`) were silently ignored by `_build_var_map` because the parser classifies them as `word` nodes rather than `macro` nodes, and the macro-resolution pass only handled `macro`-typed nodes. As a result, vertices such as `($xMin $yMin $zMin)` were missing from the 3-D view. A new word/compound arithmetic pass evaluates the substituted value as a numeric expression, so `-$xMax` resolves correctly once `xMax` is known.

- **Compare Cases: side-by-side panel now appears immediately** — The "Side by side" checkbox is checked by default. When a comparison was started, Qt's `toggled` signal was not emitted because the checkbox value was already `True`, so the comparison panel stayed hidden until the user manually unchecked and rechecked the box. ### Improvements

**BlockMesh viewer: side-by-side mode**

- A **⊞** toggle button appears in the top-right corner of the upper tab widget when `blockMeshDict` is the active file and the BlockMesh panel is available.
- Clicking it places the 3-D viewer in a horizontal splitter to the right of the Tree, so tree edits and the 3-D view are visible simultaneously. The separate **BlockMesh** tab is removed while side-by-side mode is on, and restored when it is turned off.

**Comparison panel: hidden when not in comparison mode**

- The reference-case tree pane is now hidden entirely when no reference case is loaded. Previously it occupied an invisible splitter slot, leaving a hairline splitter handle gap between the main tree and the detail pane.
- The pane appears when **Side by side** is checked in the diff bar and disappears when it is unchecked or **Clear** is clicked.

**BlockMesh viewer: Preview mode for variable-based meshes**

- When the `vertices` block contains variable references (`$varName`), the X/Y/Z cells in the vertices table are now read-only by default (direct writes would silently fail and were confusing).
- A **⚙ Variable-based** chip and a **Preview** toggle button appear at the top of the Vertices panel (inside the group box, not in the main toolbar). Clicking **Preview** enters Preview mode: table cells become editable and each change immediately updates the 3-D view, but the tree and file are not modified. A yellow banner is shown while Preview mode is active.
- Click **Refresh** to exit Preview mode and restore vertex coordinates from the tree.
- For meshes without variable references the table behaves as before: edits write through to the tree and editor immediately.

**BlockMesh viewer: multi-level variable chain resolution**

- Variable chains of arbitrary depth in `blockMeshDict` are now fully resolved. Previously, a macro reference like `z001 $z1;` would fail when `z1` itself was defined via `#eval{$z0+$dz0}` — the macro pass ran before `#eval` was evaluated, leaving the raw expression string instead of a number.
- The fix replaces the fixed three-pass approach with an iterative loop that alternates macro-reference resolution and `#eval` expression evaluation until stable. The iteration cap is the number of top-level variable definitions, which is the theoretical maximum depth of any non-circular dependency graph.
- Circular references (`a $b; b $a;`) are silently left unresolved without causing an infinite loop or crash.

## v1.4.0 — 2026-06-09

### New features

**foamMonitor launcher**

- A **foamMonitor…** button in the top bar opens a dialog to launch `foamMonitor` and plot residuals or other data with gnuplot.
- The dialog lets you pick any file (solver log or `postProcessing/` output), set options (log scale, grid, refresh interval, idle timeout), and add free-form extra flags.

- If the selected file does not exist, or foamMonitor exits with an error, a warning dialog is shown.

**BlockMesh viewer: variable and `#eval` expression support**

- Variable definitions at the top of `blockMeshDict` (e.g. `xMax 0.5;`, `nCell 20;`) are now substituted in `vertices` and `blocks` before the 3-D geometry is extracted. Both `$varName` and `${varName}` reference styles are recognised.
- Macro variables that reference other variables (`nx $nCell;`) are resolved one level deep.
- Arithmetic expressions (`zMax #eval{ $length / $nCell };`) are evaluated after variable substitution. Supported operators: `+`, `−`, `*`, `/`, parentheses.
- Previously, unresolved `$variable` references caused `float()` conversion to fail, producing missing vertices and, in the worst case, an out-of-bounds vertex index that triggered a VTK crash.
- **Lexer fix:** `#eval{expr};` written without internal spaces was tokenised as a single directive token that included the semicolon, causing the parser to consume the entire `vertices` block as the value of the preceding variable. The lexer now stops directive token reading at `{`, so depth tracking works correctly.

**Drag-and-drop to open a case**

- Drag a case directory from the file manager and drop it anywhere on the application window to open it — the tree view, editor, file list, and all other panels are valid drop targets.
- If there are unsaved changes in the currently open file, a confirmation dialog is shown before loading the new case.
