# Release Notes

## v1.15.1 — 2026-08-15

### Documentation

- **All eight demo movies re-recorded against v1.15.0's toolbar and menu changes** — the previous takes showed the old raised-button action bar, the pre-rename menu items (`Save All Files`, the un-ellipsised `Duplicate from Case Library...`/`Compare with Case...`), and the Detail pane's clipped last line, none of which match what `main` now draws. Re-driving `tools/demo_driver.py` over `tools/demo_specs.json` turned up a second, unrelated staleness in Movie 7: `system/PDRblockMeshDict` was added to `TARGET_FILES` on 2026-08-08 (v1.13.0), so the bundled `tutorials/cavity/cavity` case it demonstrates the `[+]`/"Add files" beat with no longer has anything hidden to reveal. The case gains a genuine unlisted companion file instead, `system/blockMeshDict.m4` — the m4 source `blockMeshDict` would be generated from, in the style several upstream OpenFOAM tutorials ship both files — and the scene and `docs/DEMO_SCRIPTS.md`/`_ja.md` point at that. The `.srt` caption files (tracked; the `.mp4`s are not) are regenerated alongside.

- **A side-by-side spec with no `minimized_panes` entry showed the Detail pane where the Tree should be** — a bug that has been live since 2026-08-07 (the pane-minimize/restore feature, `9a646c3`) but only now surfaced, because Movies 1 and 4 are the only demo scenes that both enable `side_by_side` and had not been re-driven since. `apply_window_state()` first toggles side-by-side mode, which as a side effect minimizes the Detail pane (`_auto_minimize_detail_for_side_by_side`, correctly giving the 3-D view the width); it then applies the scene's explicit `splitter_sizes`, which also (redundantly) put the Tree at full width; but `_apply_minimized_panes()` runs last and is unconditional — any registered pane the state's `minimized_panes` dict does not name is forced back to *restored*, which un-collapses Detail a second time and steals the width straight back from the Tree. None of `tools/demo_specs.json`'s or `tools/screenshot_specs.json`'s hand-authored scenes had ever set `minimized_panes`, relying on `splitter_sizes` alone to imply a pane was hidden — which worked until the pane-minimize feature made that implication insufficient. Fixed by adding an explicit `"minimized_panes": {"detail": 530}` to the two affected demo scenes (`damBreak-end-to-end`, `motorBike-snappy-overlay`, both re-recorded) and the one affected screenshot shot (`blockMesh3Dview-snappyHex-motorBike`, both the light and dark PNGs regenerated — they had shipped with this defect since 2026-08-12). Verified headlessly (`right_upper` splitter sizes read back after `apply_window_state`) before re-recording anything. No application code changed; every other scene in both specs was checked and is unaffected, because the bug only fires for a scene that sets `side_by_side: true` without also declaring `minimized_panes`.

- **A full sweep of the gallery and the demo movies for panel proportions turned up one more: `main-window-compare.png`'s Detail pane was unreadable.** Its three-way split (`right_upper: [370, 345, 255]`, current tree / reference tree / Detail) gave Detail only 255 px, nowhere near enough — `Choice Supported In` read `Foundation v...`, `Key Help` lost words entirely to a mid-word clip rather than a wrap (`"...for eve"` / `"term..."`, dropping `ry `), and the `Choices` combo box's dropdown arrow ran past the window edge and off the captured image, unreachable. Rebalanced to `[320, 300, 370]` — Detail now wraps its longest content cleanly with no clipping and the combo box is fully on screen; the two tree columns keep a mild value-column truncation (recoverable via the existing horizontal scrollbar, the same trade-off every other gallery shot with a narrow column already makes) rather than starving Detail for their sake. The 255 px figure had shipped since 2026-08-12 (the same toolbar/gallery regeneration as the pane-minimize bug above) and had not been looked at since; everything else in the gallery and all eight movies were checked frame-by-frame for the same class of issue (Editor squeezed too short, Tree/Detail imbalance) and are fine — including `pitzDaily-turbulence-notes`, whose Tree/Detail area looks mostly empty on an easy frame but is in fact sized for its worst case, the three-reference `SpalartAllmaras` note, which nearly fills it.

- **The demo movies moved from YouTube to Vimeo.** Re-recording all eight for the toolbar UI meant re-uploading all eight, and YouTube gives a re-upload a new URL every time — every published link (this page, README.md, RELEASE_NOTES itself) has to be found and updated in lockstep, which is exactly the kind of drift this release's demo-gallery sweep was already hunting. Vimeo lets a replacement video go up under the *same* URL, so the next re-recording won't need a link hunt at all. It also carries a caption track per language rather than one language per upload, so the query string now says which: `?texttrack=en` / `?texttrack=ja`. `docs/DEMO_SCRIPTS.md`/`_ja` and `README.md`/`_ja` are updated to the new links.

### Internal

- **Eleven keys claimed a fork that never read them.** Closing the last of the OpenFOAM 14 measurement (the generator's spec item 9) meant reading the 21 keys whose readers the previous scan could not reach — and the answer was not the expected "confirm and widen". Nine of them are read by Foundation 14 and were widened; five were read by Foundation once and quietly dropped, each now carrying a closed span and the release that stopped reading it (`maxDi` and `functions.regionType` at v13, `functions.timeEnd` at v12, `functions.formatOptions` at v8, `minTriangleTwist` at v10, joined by `functions.timeStart` at v12 which the widened scan found in passing); and **six were never Foundation keys at all** — `mergeType`, `finalOnLastPimpleIterOnly`, `functions.writeToFile`, `functions.useUserTime`, and the two `oversetInterpolation` categories with their wildcard rows. A Foundation user selecting any of them was told the key was available in a release that ignores it. `geometry.radius1`/`radius2` make eleven, and are the sharpest of the set: they were tagged "searchableCone reached Foundation in v12" on the strength of a literal `"radius1"` that belongs to `truncatedConeToCell`, an unrelated topoSet source. Foundation's searchable-surface directory has no cone in any release from v7 to v14. The tag matched a string; the wrong reader owned it. With the stragglers resolved, **`OPEN_ENDED_SERIES` is now empty** and the Detail pane's "(newer releases not yet measured)" caveat no longer appears anywhere, because there is no longer a span it would be true of.

  Getting there needed both Foundation checkouts expanded to all of `src`, `applications` and `etc` — the spec had assumed the missing readers were in solver applications, and they were actually spread across five `src/` subtrees as well. **The near-miss is the part worth keeping.** `executeInterval` was on its way into the OpenCFD-only group: it appears as a literal in no Foundation source, because the reader builds the name as `prefix_ + "Interval"`, and Foundation ships it in `etc/caseDicts/functions/mesh/checkMesh` regardless. That is the same blindness that once hid the 37 `<Model>Coeffs` keys, this time in a hand-written entry, and it is why `tools/scan_foundation14_keys.py` now reads `etc/caseDicts` beside `tutorials`, renames its third verdict from `NOT COVERED` to `ABSENT` with the warning attached, and treats a shipped key with no reader as a candidate defect rather than reassurance — the first thing that block flagged was `minFlatness`, the known-ineffective key it should have flagged. The scan also had a real defect: it walked each checkout whole, and since the newer tree had a `tutorials/` directory the older one lacked, four stray `.C` files were inflating one side of a differential comparison. It now compares named subtrees and refuses to run if they differ between the two.

- **`KeySchema` can say what happens when a key is omitted.** Two new fields, `default` and `required`, sharing one **If Omitted** row in the Detail pane — they are two answers to one question, and giving them separate rows would invite the incoherent third state where a key both falls back to something and requires you to supply it (a test forbids it). `required` is the one that earns its place: the viscosity models read `nu0`, `nuInf`, `m` and `n` with no fallback at all, and until now the only way to say so was a sentence in the description that no code could act on. An empty `default` means "not recorded", never "no default exists" — the generated turbulence modules still carry their defaults in prose, and reading the empty field as a claim would mark every one of them required. This answers the second of the three questions foamlore was blocked on for the thermophysical family (the generator's spec item 7); the other two are answered in the same change — emit the runtime-selection tables and let FoDE narrow, and use three thin per-file modules over one shared generated body, because Foundation's `physicalProperties` is the union of the two files OpenCFD keeps separate and a single merged table would be wrong in both directions at once. Item 10 is closed too: foamlore's rename census now reaches every dictionary FoDE has a schema for, and the attribution file is guarded against silent drift.

- **OpenFOAM 14 is measured, and the Foundation tags reach it.** foamlore added `foundation-14` — `OpenFOAM-dev` at tag `version-14`, commit `c046c72`, the frozen tag rather than `OpenFOAM-14`'s moving master — as its nineteenth checkout and re-derived; the vendored `schemas/_turbulence_coeffs.py` and `schemas/momentum_transport.py` are regenerated, along with the generated `THIRD-PARTY.md`, whose attribution now credits 19 checkouts and the copyright years v14's headers carry. `schemas/turbulence_properties.py` is unaffected: it names the pre-OpenFOAM-8 file, a boundary no later release moves. **Nothing moved.** Not one of the 350 (model, coefficient) pairs differs from Foundation 13, none was added, none dropped, and the model set is identical — so the three Foundation ranges in `schemas/_base.py` simply extend by one release, `FOUNDATION_V8_V13` → `FOUNDATION_V8_V14` and likewise `FOUNDATION_V9_V14` and `FOUNDATION_V10_V14`, beside a new `FOUNDATION_V14`. A Foundation 14 user selecting `sigmaNut` in `constant/momentumTransport` is now told the release they are running reads it, rather than shown a range that stops one short. What 14 *did* change is the sub-dictionary a model reads its coefficients from: `RAS { kEpsilon { … } }` is now accepted beside `RAS { kEpsilonCoeffs { … } }`, an added spelling rather than a replaced one, so every key FoDE resolves today still resolves to the same thing. [docs/OPENFOAM_VERSIONS.md](docs/OPENFOAM_VERSIONS.md) has the measurement and the one direction it bites — a case written on 14 with the new spelling and run on 13 silently takes every coefficient's default. The hand-written keys were then measured too, rather than assumed: a new `tools/scan_foundation14_keys.py` differentially scans a Foundation 13 checkout against a Foundation 14 one — differentially, because the checkouts are sparse and "absent from v14" would otherwise be indistinguishable from "reader not fetched" — and cross-checks against v14's own tutorials. **283 of 307 keys confirmed, one removed, ~21 still unmeasured**, so `FOUNDATION_SERIES` widens to `Foundation v7-v14` and only the stragglers keep a `Foundation v7-v13` label. Where a span does stop short, the Detail pane now says why: it appends "(newer releases not yet measured)" so a v14 user reads a gap in our checking rather than "unavailable in your release" — the misreading that once told OpenCFD users 61 shared keys were Foundation-only.

  The scan earned its keep immediately. **`processorAgglomerator` is gone from Foundation 14**, which replaced it with a `processorAgglomeration` sub-dictionary and provides no compatibility lookup, so the old spelling is silently ignored there; it was tagged as supported in every release, and widening the label without measuring would have turned that into a false claim. Reading the surrounding v14 code by hand turned up a second change no differencing tool could flag, because both spellings survive: **`nCellsInCoarsestLevel` is now `minCellsPerProcessor`**, with the old name still accepted. Both are corrected, and neither is marked a global rename — OpenCFD reads both spellings as current, so saying otherwise would tell those users to write keys their fork ignores. The generator's spec item 8 is now marked done; item 9 tracks the ~21 keys whose readers live in solver applications rather than `src/`.

- **Four `fvSolution` PIMPLE keys were wrong, and had been for three releases.** A by-product of the above: fetching those source subtrees also let foamlore's rename scan reach dictionaries it had never seen, and the first thing it found was already a defect here. Foundation 11 renamed `turbOnFinalIterOnly` to `transportCorrectionFinal` and has accepted both ever since; FoDE carried the old spelling as a plain current key and had no successor to name. The same file's `SIMPLErho` → `simpleRho` pair is older still — every Foundation release from v7 reads `simpleRho` — and FoDE had **neither** spelling. All four are present now, tagged per fork rather than globally: OpenCFD reads `turbOnFinalIterOnly` and `SIMPLErho` as its *current* names and has neither Foundation spelling, so marking either a rename outright would have told OpenCFD users to write keys their fork cannot read. The Foundation 11 boundary is measured across all eight Foundation checkouts, not inferred, and `schemas/_base.py` gains `FOUNDATION_V11_V14` for it. None of this was an OpenFOAM 14 problem; it only became visible because a subtree was fetched for an unrelated reason, which is recorded as the generator's spec item 10. [docs/OPENFOAM_VERSIONS.md](docs/OPENFOAM_VERSIONS.md) gained two sections from the same measurement: that the forks can disagree about which spelling is current, so "prefer the newer name" is bad advice on its own; and that **OpenFOAM 14 silently drops `processorAgglomerator`** — parallel `GAMG` now reads a `processorAgglomeration` sub-dictionary, with no compatibility lookup, so a 13-era case keeps running but stops agglomerating across processors, and three of the method names (`masterCoarsest`, `eager`, `procFaces`) no longer exist. That one bites moving *forwards*, which the page had not previously had an example of.

## v1.15.0 — 2026-08-13

### Improvements

- **The top action bar is a real toolbar now, not a row of plain buttons** — a `QPushButton` always paints a raised, bordered rectangle, so the row sat right above the **Tree** / **Boundary** / **BlockMesh** tab bar and read as a second tab strip; a user reported the buttons "look like tabs". A `QToolBar` docked with `addToolBar` fixes it structurally rather than cosmetically: its buttons default to `autoRaise` and draw flat until hovered, the same way every other toolbar on the desktop does. Each command now shows a small icon beside its label — nine new hand-authored SVGs under `ui/assets/icons/`, licensed AGPL like the rest of the repository rather than pulled from a third-party icon set, so there is no attribution obligation to track. Icons are tinted to the active theme rather than drawn once in a fixed colour, so they stay legible in light, dark, and system mode alike. **Open Case** joined the toolbar, since opening a case previously had no visible control besides drag-and-drop — `Ctrl+O` worked, but nothing on screen said so. The toolbar and the **Case** menu now share one `QAction` per command instead of building two, which is how **Save All Files** (the button) and **Save Case** (the menu item) turned out to name the identical `save_all_files` command under two different labels; sharing the action forces one label, and it is **Save Case** everywhere now. The editor's Find row got the same toolbar treatment, for the same reason.

- **The Detail pane no longer cuts off its last line** — the same wrapped-`QLabel` bug the About and Resources dialogs had (a label's `sizeHint` is measured at a width Qt guesses, not the one it is given), but harder to catch here: the pane repopulates on every tree selection and changes width on every drag of the splitter beside it, so the dialogs' one-shot fix would not have been enough. It now re-fits on every repopulation and every resize.

- **The file list elides long names instead of hiding them behind a scrollbar** — a path like `constant/transportProperties` used to grow a horizontal scrollbar in a narrow file list, so reading the tail of a long name meant scrolling sideways one row at a time. It now truncates with `…` and keeps the informative head visible; the full name was already on the row's tooltip, and header rows gained the same tooltip now that a narrow panel can elide them too.

- **Four panels that were never translated are translated now** — the BlockMesh 3-D panel had no `tr()` call anywhere in it, so every menu, button, and tooltip in it stayed in English regardless of the language setting; the comparison panel, the terminal panel, and the editor's toolbar had smaller gaps of the same kind. All wrapped, with Japanese text for each. A new test (`tests/ui/test_translatable_strings.py`) walks every string reaching a Qt display sink and fails, naming the file and line, if one is not wrapped in `tr()` — so this class of gap cannot silently reopen. Two files stay deliberately untranslated: `ui/panels/block_mesh_renderer.py` and `ui/panels/shape_mesh.py` draw their own labels directly with VTK's built-in font, which renders **nothing** for a glyph it lacks rather than a mistranslated character — a Japanese label there would not look wrong, it would not be there at all.

- **Menu tidying** — three items moved to the menu that actually owns what they act on: **Manage Extra Files & Directories…** and **Reset File List** act on one open case, not on application-wide settings, and moved from **Settings** to **Case**; **Reset Window Size** is about the window's on-screen geometry like the pane-toggle items above it, and moved from **Settings** to **View**. The **Tools** menu gained two separators, so **Run Allrun Script** (a whole workflow) and **Open Mesh in ParaView…** (a viewer, not a run) each get their own group instead of sitting in the run-a-utility list. And a full sweep applied one rule to every menu item's ellipsis: **`…` means "this will ask you for something"**, not "this will ask you to confirm". **Open Case…**, **Set Default Case Directory…**, and **Manage Schema Modules…** gained one they were missing; six items that spelled it as three literal periods (`...`) now use the real ellipsis character; and **About Foam Dictionary Editor (FoDE)**, **Keyboard Shortcuts**, and **Resources** lost theirs, since all three only display information and never ask for anything first.

### Bug fixes

- **A connected Linux build never opened a window** — `foam-dictionary-editor.spec`, the spec `build_linux.sh` actually builds, never listed `ui/xterm_terminal.html` among its bundled files. On a machine with internet access, the xterm.js download succeeds, the existence check for `ui/xterm/xterm.js` passes, and `_load_terminal()` then reads the *missing* HTML template and raises `FileNotFoundError` — unguarded, straight out of `MainWindow.__init__`, before a window ever appears. A machine with no internet access never reached that line; it took the "Terminal unavailable" fallback branch first and started normally. Internet access made the bug worse, not better, which is likely why it went unnoticed. Fixed by bundling the template. Separately, `foam_dict_editor.spec` no longer bundles `ui/xterm/` at all: xterm.js is MIT-licensed and fetched at runtime, and bundling it *only when the build machine happened to have a local cache* made the MIT copyright-notice obligation depend on build-machine state rather than on anything the spec itself controls.

- **Three status messages spliced raw English into a translated Japanese sentence** — "Parsed", "Saved", and "Parsed and tree updated" each interpolated a bare `entry`/`entries` into an otherwise-translated line, so a Japanese-mode user saw `3 件の未認識entries` in the status bar. `tests/test_i18n.py` only checked `ja.py` for duplicate keys, so nothing caught an English word riding inside a Japanese key's interpolation. Singular and plural are now separate, fully-Japanese keys.

### Internal

A six-part refactoring pass over the whole repository. Nothing here changes what the application does; the test suite went from 2235 to 2269 tests, all passing, with `ruff` and `mypy` clean throughout.

- **Three documented invariants can now fail when they are broken.** `ui/mixins/_protocol.py` is mypy's stand-in for the combined `MainWindow`, so a mixin method missing from it silently loses type checking for every *other* mixin that calls it — seven had gone missing. `tests/ui/test_main_window_split.py`'s per-mixin ownership lists, which document which mixin owns which slice of the window's surface, were about a quarter stale. And 22 test files under `tests/ui/` each defined a local `qapp` fixture that shadowed the session-scoped one pytest-qt already provides. All three are fixed, and each now has an AST guard that fails with a message naming the offending file and what to do about it; each guard was checked by reintroducing the fault. The ownership lists are deliberately *not* generated from the source — that would make the test tautological and throw away the documentation they carry — so the new check asserts the hand-written lists and the real methods agree in both directions.

- **Qt-free logic moved out of `ui/`.** Four boundary-patch helpers were living in a `QDialog` module and being imported across packages as underscore-privates; they are now `foam/boundary_patch.py`, along with the rename-boundary tree scanner, which lets its test drop the dialog import entirely. `patched_foam_monitor` and `find_backup_files` — a script rewriter and a filesystem scan, neither with any Qt in it — became `services/foam_monitor.py` and `services/backup_files.py`.

- **`ui/panels/block_mesh_renderer.py` is 478 lines rather than 863.** About 360 of them were numpy/pyvista geometry with no Qt import and no `self`, and are now `ui/panels/shape_mesh.py`. `_make_shape_mesh` becomes a module-level `make_shape_mesh()`, so the Export-STL dialog stops reaching through a panel class for a private staticmethod. Its long geometry dispatch is moved untouched — the developer guide's Update candidates section records leaving that until there is a typed geometry union to hang it on. In the same file's panel, a 218-line toolbar builder returning a bare `tuple` — which mypy could not check at the call site — became five section builders returning a `GeometryToolbar` dataclass.

- **Duplication removed where a shared home already existed, or was missing one.** `ui/widgets/_checkable_list.py` had been written for the checkable-list pattern but only two of six dialogs used it; the other four carried their own copies. In `schemas/`, `(FOUNDATION_SERIES, OPENCFD_SERIES)` was spelled out as a local constant in seven modules and inline 86 more times, and `_entry` was defined five times with five different signatures — all now one `BOTH` and one `entry()` in `schemas/_base.py`. `app_config/keyword_generator.py`'s four source scanners shared an exact skeleton around four different extractions, and now share one. `foam/tree_utils.py` gained `find_child_by_type`, and `foam/utils.py` an `is_text_only` for the script-or-log predicate three call sites were spelling out longhand.

- **The Detail pane resolves a schema key once per selection instead of four times.** Each of the four calls re-ran the full closed-namespace lookup when the resolved schema was already in hand. The registry's public accessors are untouched; a new `supported_in_text()` formats a schema or choice already resolved.

- **Some duplication was deliberately left alone**, and now says so in a comment where it is likely to be re-attempted. The four Switch-choice tuples in `schemas/` are not copies of each other: `turbulence_structure` leads with `on`/`off` because that is how the tutorials spell `turbulence on;`, and `snappyHexMeshDict` names `true`/`false` as the primary pair with the rest as alternative forms. Both orderings and both wordings reach the user in the Detail pane, so merging them would change visible text rather than remove duplication. Likewise the five overlay-menu constructions in the BlockMesh panel differ in eight or nine of nine fields including two lambdas each, so a table driving them would be larger than the code it replaced.

- **`main.py` and `i18n/` are now type-checked.** Both were already clean; the gap was that `tests/test_lint.py` claimed a coverage that `pyproject.toml` did not give it.

- **The `v2112` gap noted in v1.14.0 is closed.** foamlore added the missing `opencfd-v2112` checkout and re-derived; the vendored `schemas/_turbulence_coeffs.py` and `schemas/turbulence_properties.py` are regenerated. One entry actually changed as a result — `SpalartAllmaras.sigmaNut`'s older default (`scalar(2)/scalar(3)`, superseded by `0.66666` at v2212) was tagged with the explicit pair `"OpenCFD v2106, OpenCFD v2206"`, which read as "v2112 was checked and skipped it"; with v2112 now measured and present, it collapses into a genuine closed range, `OPENCFD_V2106_V2206` ("OpenCFD v2106-v2206") — a new constant in `schemas/_base.py`, the same family as the `FOUNDATION_V8_V13` / `OPENCFD_V2212_V2606` pair v1.14.0 already added, but for an entry superseded partway through the span rather than one still current. The generator's spec item 6 is now marked done.

- **A new `ui/icons.py`, and new guard tests.** `icon(name) -> QIcon` tints the nine hand-authored toolbar/menu SVGs for the active theme by compositing the tint through the glyph's own alpha rather than substituting a colour string into the source, so a black icon going invisible in dark mode is structurally impossible rather than a rule to remember; `tests/ui/test_icons.py` includes the dark-mode regression check for exactly that. `tests/ui/test_translatable_strings.py` and the `tests/test_i18n.py` extension are the two i18n guards described under Improvements above; `tests/ui/test_action_toolbar.py` and `tests/ui/test_detail_panel_fit.py` cover the new toolbar and the Detail pane's repeated-fit behaviour respectively.

## v1.14.0 — 2026-08-10

### Improvements

- **Text sizes now follow the desktop's font setting** — the editor, the simple terminal and the xterm terminal each used to name a size outright (10 pt, 10 pt, and 13 CSS px), which on a desktop whose font is larger than that made the two panels holding the actual text the smallest thing in the window, and left them unmoved when the font size was raised to cope with a dense display. Eight more labels did the same in pixels — the BlockMesh panel's mouse-hint line and "⚙ Variable-based" badge, and the About and Resources dialogs' name, version, licence, acknowledgements and disclaimer lines. All of them now derive their size from the application font, so raising the desktop's font size grows the whole window together. Nothing to configure: it is the setting you already have.

- **Settings > UI Scale**, for displays where the desktop does not tell Qt the truth — 100 % (default), 125 %, 150 %, 175 % or 200 %, saved in `app_config.json` and applied on the next start. On X11, Qt works out its scale factor from the `Xft.dpi` X resource and nothing else, so a session that scales through `GDK_SCALE`, or a fractionally scaled XWayland one, leaves every Qt application drawing at 1× while the GTK applications beside it look right — the usual reason a window comes out looking half-size on a high-resolution panel. `python3 main.py --ui-scale 150` applies a scale for one run without changing the saved setting, and accepts anything from 50 to 400. A `QT_SCALE_FACTOR` already in the environment wins over the saved setting, since it was chosen for the machine in front of you; the command-line flag overrides both. USER_GUIDE.md's new "Text size and display scaling" section covers the `Xft.dpi`, `QT_FONT_DPI` and rounding-policy escape hatches as well.

- **The editor text can be zoomed on its own** — `Ctrl` + `+` / `Ctrl` + `-`, `Ctrl` + `0` to go back to the desktop's size, and `Ctrl` + scroll wheel. The keys are bound to the editor rather than the window, so they never fire from the tree or the 3-D viewer. The zoom is kept as an offset from the desktop's font size rather than a fixed size — two steps up stays two steps up if that font later changes — and is saved with the session, so it survives a restart.

- **Apply Text to Tree and Reload from Tree moved to the seam between the tree and the editor** — the two commands were in the top action bar next to Save File and Reload Case, which grouped them with the disk operations they have nothing to do with and put them a full window height away from the editor text they act on. Worse, the pair reads as two near-identical strings that have to be parsed carefully to tell apart. They now ride the top-right corner of the lower row's tab bar — the boundary between the tree above and the editor below — and carry the arrow that makes the direction obvious: **▲ Apply Text to Tree** parses upward into the tree, **▼ Reload from Tree** regenerates downward into the editor text. A corner widget rather than a row inside either tab page, for two reasons: it costs no vertical space (it shares the tab bar's row and stays clear of the splitter handle), and it stays visible whichever tab either row is showing. That second point is not cosmetic — **Apply Text to Tree** is still what refreshes the BlockMesh 3-D overlays while the **BlockMesh** tab is in front, so hiding it behind a tab selection would have put it out of reach exactly when it is wanted.

- **Panes can be minimized in one click, and put back the same way** — the file list, the Detail pane beside the tree, and the Editor/Terminal row along the bottom. Dragging a splitter handle across the window already did this, but it costs several mouse moves and leaves you hunting for the handle to undo it. There are now three equivalent ways: the **View** menu (**File List** `Ctrl+1`, **Detail Pane** `Ctrl+2`, **Editor / Terminal Pane** `Ctrl+3`; ticked means shown), a **▁** button on the right of the Editor/Terminal tab bar for the bottom row, and a **double-click on any splitter handle** next to a minimizable pane.

  The bottom row is treated differently from the other two on purpose. The file list and the Detail pane collapse to nothing; the Editor/Terminal row stops at its **tab bar**, so the Editor and Terminal tabs stay clickable and **▲ Apply Text to Tree** / **▼ Reload from Tree** stay where they were rather than disappearing with the pane. Collapsing that row to zero was not an option in any case: its splitter deliberately disables collapsing so the handle drags smoothly instead of snapping, and under that setting a request for zero height silently clamps to 136 px.

  Entering side-by-side mode now parks the Detail pane for you and restores it on the way out, since a file being inspected in 3-D has little use for it and the width is better spent on the view. A pane you minimized by hand first stays minimized when side-by-side ends. ### New features

- **The Detail pane now shows what OpenFOAM says about a coefficient, not only what its default is** — a value tells you what the solver will do; it cannot tell you what the coefficient means or when to change it. OpenFOAM's own headers do, and foamlore now extracts that prose and carries it into the generated schemas, quoted verbatim with the file and line it came from. Selecting a `<model>Coeffs` dictionary shows the model's description from its header — every one of the 29 models has one — with the paper that defines it in the Note row, so `kEpsilonCoeffs` cites Launder & Spalding and `GEKOCoeffs` cites Menter & Matyushenko (2025). Selecting a coefficient that upstream documents on its declaration leads with that: `F3` reads "Flag to include the F3 term" before the mechanical default sentence, and 257 coefficients carry one.

  The case that prompted it is rarer and more useful than either. GEKO's `CFbLam` is written in the source as `1.0  // increase to 25 in case of transition simulations (MM:p. 4)` — the comment says *when* to change the coefficient, and `MM` is a tag into that model's own reference block. That note is now on the key, and the citation resolves against the reference shown on the dictionary above it. Long quotes are trimmed for the pane and marked as trimmed; foamlore's `get_fact` returns the full text with its citation.

All 27 model choices in the two selectors are covered; `laminar` is not a model class, so it keeps the short hand-written line. It now has a registry where a model is one table row, and coverage went to **16 RAS models and 13 LES/DES models** — every model either fork ships — measured across all seventeen releases: `kOmega`, `kOmega2006`, `realizableKE`, `RNGkEpsilon`, `LaunderSharmaKE`, `LRR`, `SSG`, `EBRSM`, `GEKO`, `kEpsilonPhitF`, `v2f`, `kOmegaSSTLM`, `kOmegaSSTSAS`, the `Smagorinsky`/`WALE`/`sigma`/`kEqn`/`dynamicKEqn`/`dynamicLagrangian`/`DeardorffDiffStress` LES set, and the `SpalartAllmaras`/`kOmegaSST` DES, DDES and IDDES families. ### Bug fixes

- **Schema help for `fvSchemes` never appeared at all** — the module wrote its keys the opposite way round from the way they were looked up, so every one of its entries was unreachable: selecting `ddtSchemes/default` offered no description and no list of schemes, in every case, since the module was written. Its unit tests passed because they asserted the internal table shape rather than the call the Detail pane makes. The keys are corrected, and a new test parses real tutorial dictionaries and walks them the way the pane does, so a module cannot go dark again without the build failing.

- **New built-in schemas reach existing installations** — the saved schema module list was authoritative, so anyone who had opened **Settings > Manage Schema Modules** even once was pinned to the modules that existed that day and never received a later one. The built-in defaults are now merged into the saved list on every load, and only modules you explicitly removed stay out. If you removed one before this release there was no record of the intent, so it will reappear once and can be removed again.

- **`blockMeshDict`'s `mergeType` no longer offers an invalid value** — the dropdown listed `merge`, which OpenFOAM does not accept, and omitted the real default `topology`; the two descriptions were also swapped. Choosing from the list produced a dictionary blockMesh could not read as intended.

- **Version labels no longer claim shared keys are Foundation-only** — 61 entries, including all of `fvSchemes` and most of `fvSolution`, were tagged as Foundation v13 despite belonging to the `finiteVolume` and `lduMatrix` libraries that both forks share, telling OpenCFD users that core keys were unavailable to them.

- **A sub-dictionary's schema help no longer borrows another's keys** — the Detail pane resolves a key by looking first for it under the surrounding dictionary's name and then, failing that, for a plain entry of the same name. The second step had no sense of where it was: a key written inside one named sub-dictionary could be answered by an entry that belongs to a different one, described confidently and offered with a default value that does not apply there. A dotted prefix is now a closed namespace — once a schema module qualifies any key under a name, a key it does not qualify there is not that dictionary's key, and the flat fallback stays quiet instead of guessing. Keys that no namespace claims are untouched and still fall back from anywhere, which is what keeps the flat spelling of a dictionary that OpenFOAM reads through `optionalSubDict` working, and what leaves every `snappyHexMeshDict` lookup exactly as it was — none of its nine sub-dictionaries has a key with a flat twin, so the rule cannot fire there at all. The saving is not that the pane says less: it is that it stops attributing one thing's meaning to another, which a reader has no way to catch from the pane itself.

- **`constant/regionProperties` now opens as a proper entry** — the file that names a multi-region case's regions used to be the one file about that case you could not read in the tree. `regions ( fluid (bottomAir topAir) solid (heater leftSolid rightSolid) );` came out as two nameless amber rows, one holding the bare word `regions` and the other the whole parenthesised body, because the `regions` key was routed unconditionally to the named-dictionary parse that `setFieldsDict` needs (`regions ( boxToCell { … } );`) and anything not in that shape was treated as a failure. The key is now decided by the same lookahead `sets` and `surfaces` already use: named dictionaries still parse to `region_block`/`region_entry`, so the setFields overlay is unchanged, and everything else falls through to the ordinary list handling — exactly what an identically shaped entry under any other key already produced. Across the v2512 tutorials this takes the number of `regions`-bearing files reporting a parse error from 45 to 24, with no change to the 135 files that parse as a `region_block` and no difference to any file's byte-for-byte round trip.

- **Most of the tutorial dictionaries that failed to parse now open** — three defects in the value reader accounted for the bulk of every parse failure across the 4435 dictionary files in the v2606 tutorials: 288 files reporting 861 errors are now 38 files reporting 217. The first was a dictionary written inside an entry's value, as `fvSchemes` does in `div(phi,Yi_h) Gauss multivariateSelection { O2 limitedLinear01 1; … };` — the reader tracked brace depth but had no case for a `;` inside the braces, so the entry degraded to a nameless amber row, the block's own entries were stranded as siblings of the dictionary that should have contained them, and the closing `};` then ended `divSchemes` early, leaving every later `div(...)` parsed as a top-level node. The tree showed a structure the file does not have. The second was an entry with no value at all — `fluxRequired { p; pcorr; }`, `cache { grad(U); }` — where the key carries the whole meaning; each came out as a nameless raw row that had lost the field name that was its entire content, and schema help had no name to look up. Those are now a `valueless` node type: the key stays editable, the Value column is not, because there is nothing there to edit. The third was a comment between a key and its opening brace, which `thermophysicalProperties` writes as `mixture // air at room temperature (293 K)` on the line above the `{`; the comment is now kept and written back on the key's line, where the source had it. Round-trip fidelity is unchanged throughout — all 4435 files still write back byte-identical — because a failed entry was always preserved verbatim; what these fix is what you can see and click, not what lands on disk. The 217 errors that remain are four causes with clear shapes rather than a long tail, and each is recorded in `DEVELOPER.md` with the trade-off that has so far kept it open.

- **`snappyHexMeshDict`'s version labels are measured rather than assumed** — the correction above for 61 core entries left the snappy package still carrying the same blanket Foundation v13 tag, so selecting `snap` reported "Foundation v13, OpenCFD v2106-v2606" for a key that has existed since at least v7, which reads as "not available to you". ## v1.11.0 — 2026-07-31

### New features

- **FoDE reopens where you left it** — closing the application now records the shape of the window and what was in it, and the next launch puts that back: window size and position, the splitter positions, the active upper and lower tabs, the Terminal's mode, the case directory and every file that was open in it, which file was on screen, the selected tree row, and the BlockMesh panel's toggles, label size and camera angle. The 3-D view in particular comes back at the angle you left it rather than the default one, which previously meant re-orienting the same case by hand at the start of every session. Nothing about a saved session can stop the application opening: a case that has been renamed, a file that has been deleted, a tree row that no longer exists or a layout written by a later version of FoDE is skipped part by part, the rest is restored, and a line in the status bar names what was left out. Throwing one away is **Settings > Forget Saved Session**, which discards every variant's stored layout and greys itself out when there is nothing left to forget — a checkbox that says one thing should not quietly do the other, and the case paths a layout records are worth being able to clear on purpose. `python3 main.py --no-restore` skips the restore for one launch without touching the setting or the stored session. Each `--variant` keeps its own layout, since variants change which panels and tabs exist.

- **`--theme` on the command line** — `python3 main.py --theme dark` launches in a colour theme for that run only, leaving the saved **Settings > Appearance** setting untouched. The theme setting has always needed a restart to take effect, which made comparing the two a matter of changing the setting, restarting, and changing it back; now two windows in different themes can sit side by side, and neither of them decides what the next launch looks like. `system`, `light` and `dark` are all accepted, the same three choices the Appearance menu offers. Without the flag nothing changes: the saved setting is used exactly as before.

Sampling is the awkward one of the four overlays to see working: it has no dictionary of its own, being writable as a function object inside `controlDict` or as a standalone dictionary, and the standalone form accepts two different member-list syntaxes. Nothing in the OpenFOAM tutorials exercises more than a fraction of that — across the whole v2512 and v2606 tutorial sets, only two cases define a sampling plane at all, and none combines one with probes and lines. This case puts all of it in one 3×3×3 block: probe points, a span-based line, a point cloud, and both plane spellings, spread across a `controlDict` `functions {}` block and two standalone dictionaries written in the two different syntaxes, plus a non-geometric `patch` surface and a non-sampling function object so the difference between "listed without geometry" and "ignored entirely" is visible too. ### Bug fixes

- **The clipped-shape mark in the 3-D viewer is visible again** — an overlay shape too large for the block mesh is drawn cut down to it, and its name badge carries a mark so the cut is not mistaken for the shape's real extent. That mark was `✂ clipped`, and the scissors reached the screen as nothing at all: these labels are drawn by VTK rather than Qt, and VTK's built-in label font has no glyph for it, so it drew no glyph — not even a placeholder box — while the badge still reserved the width. What you saw was `midPlane   clipped` with an unexplained gap in it. The marks are now `(clipped)` and `(outside block mesh)`, in plain ASCII and parenthesised the same way the overlay menus' own `(no geometry)` rows are. Square brackets turned out to be no good either — VTK's font renders them as parentheses — which is worth knowing before putting any symbol in a 3-D label.

- **The 3-D viewer's X/Y/Z extents readout shows what separates its two numbers** — the same missing-glyph problem, in a second place. The **Dimensions** overlay writes each axis as `X  -5 → 15  (20 m)`, and the arrow was drawn as nothing, so the readout arrived as `X  -5   15  (20 m)`: two numbers with an unexplained gap between them, and no indication that they were the ends of a range rather than, say, a value and a count. It now reads `X  -5 .. 15  (20 m)`. A hyphen would have been the obvious choice and is the wrong one, since a range starting at a negative number would read as `-5 - 15`.

- **The 3-D viewer's orientation axes are legible in the dark theme** — the small X/Y/Z triad in the bottom-left corner of the BlockMesh viewport was the one part of the 3-D scene that ignored the colour theme. Its letters were left at PyVista's default black in all three modes, so against the dark theme's `#2E3238` viewport background they were all but invisible. They now take the same colour as the bounds readout above them, which was already themed. The axis arrows keep their conventional red/green/blue in both themes — those identify the axes rather than decorate them, the same rule the patch and overlay colours follow.

- **The 3-D grid's tick labels no longer read as faintly as the gridlines they sit on** — the grid's numbers and axis titles were drawn in whatever colour the gridlines were given, because VTK's `show_grid` paints lines and text from a single value. That colour is deliberately faint, which is right for a gridline and wrong for a number you are meant to read: on the light theme's white viewport it left them at 3.95:1, below the 4.5:1 a body of text wants. The two are now separate settings, so the lines stay exactly as faint as before while the text moves to 7.5:1 on the light theme and 7.7:1 on the dark one. Dark mode was already adequate at 4.58:1, so this was a light-theme problem that the dark-theme work happened to surface. The colour table's own legibility test is what let it through: it held every viewport colour to 3.0:1, which is the right target for lines and the wrong one for text. It now checks text at 4.5:1 and leaves the gridlines at 3.0:1.

- **An overlay shape cut down to the block mesh is no longer hollow** — a shape mesh is a hollow surface, and the cut left it open, so a shape with both of its end caps outside the clip box came back a tube with nothing inside. That is the ordinary case rather than a corner one: a `setFieldsDict` region is conventionally written to span the whole depth of a quasi-2-D case — damBreak's `box (0 0 -1) (0.1461 0.292 1)` against a tank 0.0146 m deep — and the front view is the one angle such a case is ever looked at from, so the initial water column appeared as an empty orange outline drawn over the mesh rather than as a filled region. Each cut is now sealed and a clipped shape reads as a solid, the same way an unclipped one always has. Cylinders gain the most: their seam carries duplicate points that made them fail the closed-surface test outright, and merging those points first is what allows them to be capped at all. Shapes with no volume to seal — a `planeToFaceZone` plane, a sampling disc — keep exactly the behaviour they had. Nothing about what the clip *means* changed: the dictionary and the extracted geometry are untouched as before, and **Export Shapes as STL…** still writes the full shape.

- **Reset All Settings now actually resets the application settings** — the dialog deleted `app_config.json` and said so, but the application went on running, and closing the window wrote the file straight back: the shut-down captures the session layout and the window size, so the settings the reset had just removed came back with the next launch. The saved session was the visible half of this — resetting the settings and reopening FoDE put you back in the same case, in the same layout, which is the opposite of what was asked for — but every key in the file was affected in the same way, `window_size` included. The deletion now holds: once the application settings have been reset, closing the window persists nothing, so the next launch starts from the defaults. That is what the dialog's "please restart the application" has always meant, and the completion message now says what it costs, namely that the layout and size of that session are not saved. Settings you go on to change deliberately after the reset — picking a theme, say — are still saved as before; only the automatic capture on the way out is suppressed. Resetting the schema settings is unaffected, since `schema_config.json` has never been written at shut-down.

- **The Reset Settings dialog no longer describes settings that do not exist** — the tooltip on **Application Settings (app_config.json)** read "Reset case directory, window size, and recent cases". There is no recent-cases feature, and the file has since grown to hold the theme, the language, the case library, your links, the OpenFOAM installation directory and the saved session, none of which were mentioned — the saved session least excusably, since that is the part of a reset people notice. The tooltip now lists what is actually reset. The confirmation dialog's text, which was assembled from untranslated English fragments while its Japanese translations sat unused in `i18n/ja.py`, is now translated too.

## v1.10.0 — 2026-07-30

### New features

- **Files pulled in by `#include` are now listed and readable** — a dictionary that says `#include "caseSettings"` or `#includeEtc "caseDicts/setConstraintTypes"` used to leave FoDE with nothing to show: the directive was stored as opaque text and the file it named was invisible, even though understanding the case often depends on reading it. Those directives are now resolved and the files they refer to appear in the file list, marked `↳`. An include landing inside the case joins the group it belongs to, so `constant/caseSettings` shows up under **constant** and is editable like anything else. One that resolves into your OpenFOAM installation — which is where roughly half of them go, `#includeEtc` alone accounting for 560 of the 1,081 directives in the v2512 tutorials — is collected in a new **included files** group at the bottom, in italic, with a tooltip naming the file that included it. Nothing is merged into the including dictionary: the included file stays a file of its own, the way a symlinked file does, and the directive keeps its own tree row. Right-clicking that row offers **Open Included File** (double-clicking its Key or Type cell does the same), and hovering it reports what the directive resolved to — or that the target is missing, that an optional `#sinclude` is simply absent, or that no OpenFOAM installation was found to resolve `#includeEtc`/`#includeFunc` against. All five directive forms are handled, including `<case>`/`<system>`/`<constant>`/`<etc>` path tokens, `$FOAM_*` variables, and `#includeFunc mag(U)`-style arguments; 1,072 of the 1,081 directives in the v2512 tutorials resolve, the remaining nine being files that `Allrun` generates and that genuinely do not exist yet in a pristine case. Includes are followed one level only, and a C++ header included inside a `#codeStream` body is deliberately ignored rather than offered as a dictionary.

- **Files from the OpenFOAM installation are read-only, with a one-click way to make them yours** — an `#includeEtc` target lives inside your OpenFOAM installation and is shared by every case on the machine, so editing it in place would be a mistake that is hard to notice and harder to undo. Such files open normally — full tree, full text, syntax highlighting — but the editor is locked and shows a `read-only` badge, tree entries cannot be edited, and Save, Save All, Create Backup, Duplicate and Delete are all unavailable rather than silently writing where they should not. **Copy into case...** on the file's context menu is the way through: it copies the file into your case, defaulting to `system/`, which is exactly where OpenFOAM looks before consulting its own `etc/` — so for `#includeFunc` the copy takes effect with no edit to the directive at all. The copy is a normal, editable case file and is registered in the file list so it survives later changes to the directive. Unsaved edits in other open files are preserved across the copy.

- **`blockMeshDict`'s blocks now appear one per row in the Tree view** — the `blocks ( … );` entry used to arrive as a single row holding every block as one long string (five blocks and roughly 380 characters, in the `pitzDaily` tutorial), even though the BlockMesh 3-D viewer had always drawn them as separate, individually coloured and numbered blocks. It now expands to `block 0`, `block 1`, … in the same order and with the same numbers the viewer draws at each block's centre, so the two views finally refer to the same thing. Each row is editable on its own and hovering shows a breakdown of the block's vertices, cell counts, grading, and zone; clicking a row scrolls the Editor tab to that block rather than to the top of the list. Round-trip fidelity improves as a side effect: editing one block used to reflow the entire list onto a single line, and now leaves every other block byte-for-byte as it was. Lists that aren't a plain sequence of `hex` blocks — an empty list, or one built from macros — keep their previous single-row behaviour, so nothing that parsed before parses differently now. A list that mixes an `#include` in with its blocks does expand: the directive gets a row of its own among the blocks, and the block numbering steps over it so it still starts at 0 and still matches the viewer. One consequence worth knowing: in compare mode, blocks are matched by position, so a file where two of five blocks differ is now marked `≠2` where it previously showed `≠1`.

- **Blocks can be added, duplicated and deleted from the Tree view, and the selected one is highlighted in 3-D** — the two things left over from showing `blockMeshDict`'s blocks one per row. Right-clicking a `block N` row now offers **Add Entry After**, **Duplicate** and **Delete** like any other entry; a newly added row starts as a real `hex (0 1 2 3 4 5 6 7) (10 10 10) simpleGrading (1 1 1)` block rather than an empty placeholder, so it survives the next **Apply Text to Tree**, and deleting one renumbers the rows after it automatically. Selecting a block row outlines that block in the BlockMesh 3-D viewer, which works because the row number and the number the viewer draws at each block's centre are the same number — the outline shows even with **Block edges** and **Solid blocks** both switched off, and clears when you select anything else. **Comment Out** stays unavailable on block rows: a commented-out block inside `blocks ( … )` reads back as a comment rather than an entry, so the row would disappear instead of being restorable.

- **Colour theme setting (Settings > Appearance)** — a new **Follow System** / **Light** / **Dark** choice, saved in `app_config.json` and applied on restart. **Follow System** (the default) keeps the platform's native widget style and desktop palette; **Light** and **Dark** force the Fusion style with FoDE's own palette so the window looks identical on every OS. Dark mode retunes the whole UI, including the editor's syntax highlighting, the line-number gutter, diff row backgrounds, the notice banners, and the BlockMesh 3-D viewer — whose scene background, axis/bounds text, vertex and block labels, and shape name badges follow the theme too, instead of the viewer staying a fixed white rectangle inside a dark window. Every colour the UI draws now resolves through one table in the new `ui/theme.py` instead of being hard-coded across a dozen files, so the two themes cannot drift apart — the diff legend swatches and the tree's diff row backgrounds, for instance, now read the same values by construction.

- **The BlockMesh 3-D panel's Load STL / OBJ dialog now accepts several files at once** — the viewer has always been able to show any number of STL/OBJ overlays, but the file chooser only let you pick one per visit, so a snappyHexMesh case with a folder full of surfaces in `constant/triSurface/` meant reopening **STL ▾ > Load STL / OBJ…** once per file. The dialog now allows a multi-file selection and loads everything chosen in one pass, still adding to whatever is already on screen. If one of the selected files can't be read, the others are still loaded and a single warning names the ones that failed, instead of the first bad file ending the whole load.

- **Each loaded STL/OBJ surface now has its own row in the `STL ▾` menu** — the viewer kept loaded surfaces as anonymous meshes and threw away the path each came from, so once several were on screen there was no way to tell what was loaded, hide one, or remove one: **Clear STL** dropped all of them or nothing. Every file now gets a checkable row listing its name, in its own colour from a pale palette so surfaces stay apart in the 3-D view, alongside a **Show loaded surfaces** master toggle and **Show all surfaces** / **Hide all surfaces** — the same arrangement the topoSet, snappyHexMesh, setFields and sample menus have always had. An **Unload ▸** submenu removes a single file, and loading a file that is already loaded re-reads it into its existing row instead of stacking a duplicate, which makes it the way to refresh a surface edited outside FoDE. A surface loaded on its own, with no `blockMeshDict` open, is also drawn now — it used to be loaded and listed but never rendered, because the viewer skipped drawing entirely when there was no mesh or dictionary overlay to show.

### Bug fixes

- **Dictionaries using `${...}` macro references, or a macro without a trailing semicolon, now parse** — two spellings OpenFOAM accepts had never been understood, and either one turned a whole file into a "Text was loaded, but tree update failed" warning with an empty tree. The first is a braced macro reference, which may carry a scope path: `${../_bladeForces};` in `propeller1/system/bladeForces`, `${__settings}` in the `gasMixing` sampling dictionaries. FoDE's lexer ended a word at the `{`, so a bare `$` was left standing as an entry key and the parser then failed demanding a `;`. The second is a macro used as a complete statement with no terminator at all — `maxX { $minX }` in several `pointDisplacement` files, `"pcorr.*" { $p … }` in four `pimpleFoam` `fvSolution` files — which the parser required a `;` after. Between them these accounted for **every** remaining parse failure across the OpenFOAM v2512 tutorials: measured with `tools/roundtrip_corpus.py` over the 9620 files under `system/`, `constant/`, `0/` and `0.orig/`, 9501 parsed before and all 9620 do now, with the byte-identical round-trip rate staying at 100%. The 119 files affected are not obscure — they include `system/snappyHexMeshDict` in four mesh tutorials, `createBafflesDict`, `fvSolution`, and the header-less sampling fragments in `system/` (`sampling`, `fieldTransfer`, `avg-tracer0`). Because the `;` is genuinely optional it is no longer stored as part of the entry, and the writer reproduces whichever form the file used, so editing a bare `$p` no longer silently adds a semicolon it never had.

- **Saving a file no longer rewrites blank lines you never touched** — opening a tutorial case and hitting Save reformatted the file even with no edits made: the blank line after the `// * * *` header banner moved to above it, gaps of two or more blank lines between entries collapsed, several entries written on one line (`x1 14; x2 6;`) were exploded onto separate lines, and the closing `// ****` footer banner was deleted outright. This affected every one of the 439 parseable `system/blockMeshDict` files in the OpenFOAM v2512 tutorials. Measured across the tutorials as a whole — every file under `system/`, `constant/`, `0/` and `0.orig/`, of which 9501 parsed at the time of this fix (the macro-entry fix below later took that to all 9620) — 286 saved back byte-for-byte identical before this release, and every parseable file does now. `tools/roundtrip_corpus.py` is that measurement, so the figure can be re-run against any installation rather than taken on trust. The cause was the writer adding a line break that the parser had already recorded as belonging to the next entry, plus two blunt regular expressions that tried to undo the doubling and removed real blank lines with it; the footer banner, which follows the last entry and so belongs to no entry, was simply discarded at parse time. Saving an edited file now rewrites only the entries actually edited, and a file that ended without a final newline keeps ending without one.

- **A dictionary written `divSchemes { … };` no longer moves its semicolon to a line of its own** — a `;` after a closing `}` is redundant but legal. FoDE parsed it as a separate entry, reported it in the status bar as an unrecognised entry, and on save pushed it onto the next line. This was the sole remaining reason a file changed on save without being edited — 54 dictionaries in the v2512 tutorials, mostly `fvSchemes`, which is what closed the gap to all 9501 then parseable. The `;` is still its own entry — it is real text and has to be written back — but it is no longer counted as a parse failure, and the writer now keeps an entry that touched the previous one in the source on that same line instead of assuming it needs a fresh one.

- **Editing an entry inside a block no longer shifts it to the right** — an edited entry that sits inside a dictionary was rewritten with its indentation doubled: change `nCorrectors` inside `PIMPLE { … }` and it moved from four spaces to eight, and the deeper the nesting the further it drifted. This hit the first line of every kind of nested entry — a plain `key value;`, a sub-dictionary's name, an `#includeFunc` directive, a `$macro`, a `regions`/`actions` entry, a `fieldValues` block — so any tree edit or **Use this value** on a nested key left a visibly misaligned line behind. The writer was prepending its own indentation on top of the indentation it had already reproduced from the source. Individual blocks in `blocks ( … )` were the one case that had been compensated for, which is why this went unnoticed.

- **Case Library dialog module no longer fails to import on Python 3.10/3.11** — `ui/dialogs/case_library_dialog.py` used an f-string that reused the same quote character for its outer and inner (nested `tr(...)`) string literals, which is a Python 3.12-only syntax relaxation and raised a `SyntaxError` on 3.10/3.11 as soon as the module was imported (i.e. on first opening **Case > Manage Case Library…**). The nested string now uses single quotes so the file parses on all supported Python versions.

- **The Detail panel now shows the value of a selected field entry** — selecting a `field_value` row (e.g. a `value uniform (0 0 0)` entry inside a `0/` field file's `boundaryField`) called a formatting method that no longer exists on the tree model, raising an `AttributeError` inside the Qt slot: the app kept running, but the Detail panel's value box stayed empty and a traceback was printed to the console. The panel now calls the actual formatter in `foam/utils.py`. Found by extending the type-checker to `ui/`.

- **Case > Duplicate Case… again pre-fills the destination folder** — the dialog was constructed with the main window passed positionally where the default destination-parent string was expected, so Qt treated it as a widget parent for the text field: the destination-parent box opened empty instead of pre-filled with the case's parent directory, and the dialog itself was unparented. Found by extending the type-checker to `ui/`.

- **STL/OBJ overlays no longer follow you into the next case** — surfaces loaded into the BlockMesh 3-D viewer through **STL ▾ > Load STL / OBJ…** stayed loaded when you opened a different case, so geometry belonging to the case you left was redrawn over the new one's mesh, and **Clear STL** was the only way to get rid of it. Opening a case already reset everything else the panel shows — the topoSet/snappyHexMesh/setFields/sample overlays and their menus, the vertex table, the 3-D scene — and it now clears the loaded surfaces along with them.

- **Selected rows are no longer unreadable on Windows 11** — Qt takes the selection fill from the desktop (on Windows, the accent colour from *Settings > Personalization > Colors*) but takes the selected-row text colour from the system palette independently, and nothing checks that the two work together. On Windows 11 this rendered near-black text on a saturated blue selection in the tree and file list. FoDE now recomputes the pair itself in all three theme modes. Note that the obvious fix — pick whichever of black or white has more contrast — reproduces the bug rather than fixing it: the default Windows 11 accent `#0078d4` scores 4.64:1 against black and only 4.53:1 against white, so black wins on the numbers while still being the combination that is hard to read. The rule applied instead follows what desktops actually do: white text whenever it reads adequately on the fill, dark text only on a genuinely light fill (a yellow or pastel accent), and otherwise the fill is darkened slightly — keeping its hue, so the user's accent colour stays recognisable — until white clears. Linux and macOS were unaffected but go through the same path.

- **A `#include` among the blocks no longer collapses them into a single row** — the same `blockMeshDict` that pulls patches in from another file does it for blocks too (`blocks ( #include "blockMeshDict.caseBlocks" hex … );`), and the directive made the whole list fall back to one long unexpandable row, so none of the 24 blocks written in the file could be selected, edited or highlighted individually even though the 3-D viewer drew all of them. The directive now takes a row of its own among the block rows. Its own contents stay invisible — in the tutorial case it is a symlink `Allrun` creates at run time, pointing at one of two alternative block files, so there is nothing to read at edit time — which means the numbering counts the blocks written in this file only, exactly as the 3-D viewer already did. That is what keeps `block 0` in the tree and the `0` drawn in the viewer the same block; both can differ from blockMesh's own numbering once it resolves the include.

- **A `#include` among the patches no longer costs a `blockMeshDict` its boundary** — a boundary block that pulls part of its patches in from another file, as `boundary ( #include "blockMeshDict.caseBoundary" outlet { … } );` does, failed to parse as a boundary: the whole block fell back to raw text, was reported as two unrecognised entries, and lost its editable patch rows in the Tree view. The 3-D viewer then drew it wrongly rather than not at all — the fallback text scanner read `include` as a patch name and handed it the *next* patch's faces, so in the one v2512 tutorial written this way (`compressible/rhoPimpleFoam/laminar/helmholtzResonance`) the `outlet` patch disappeared from the viewer and a phantom patch named `include` took its 9 faces. The directive is now parsed as an entry in its own right, sitting among the patches, so everything around it keeps its structured parse: the tutorial above now reports no parse errors and shows `outlet` (patch) and `sides` (symmetry) with the right faces. Files that use `#include` this way still save back byte-for-byte identical, and the round-trip figure above is unchanged.

- **Two sampling dictionaries with the same filename no longer hide each other in the 3-D viewer** — the `sample ▾` overlay tracked its loaded files by filename alone, so if a second dictionary with the same basename came into view — reachable by adding an extra directory that holds its own `sample`, `probes` or `surfaces` — the newer one silently replaced the older one's shapes in the menu, and the remaining rows named the wrong source file. Files are now tracked by their full path, while the menu rows still show just the filename.

## v1.9.0 — 2026-07-22

### New features

- **Undo/redo for tree edits** — every tree-side change is now undoable with **Ctrl+Z** / **Ctrl+Shift+Z** while the tree has focus (also in the tree context menu as **Undo Tree Edit** / **Redo Tree Edit**): inline cell edits, Detail-panel applies, Paste Value, Add/Duplicate/Delete/Comment Out/Restore from Comment, "Use this value" from compare mode, **Apply Text to Tree**, BlockMesh vertex drags, and the Boundary tab's patch operations. Undo is one global history for the session (up to 50 steps, cleared on a case switch): Ctrl+Z reverses the most recent change wherever it happened and switches to the affected file if needed; the text editor keeps its own native undo for free-form typing, and the delete confirmation no longer claims deletion "cannot be undone" — it can.

- **Sampling overlay in the 3-D viewer (`sample ▾`)** — the BlockMesh panel gained a fourth overlay source: sampling definitions are drawn in teal on the block mesh, so probe positions and sample lines/planes can be checked against the geometry before running. Definitions are read from `controlDict`'s `functions {}` block **and** from standalone sampling dicts — `system/sample`, `system/probes`, `system/surfaces`, `system/singleGraph` (including the `.org` style with top-level `start`/`end`) — which now also appear in the file list; several files contribute at once and each menu row is tagged with its source file. Non-drawable entries (e.g. `patch` surfaces) are listed under **Non-geometric sources (N)**, and the usual overlay clipping ("✂ clipped") applies. Like the other overlay dicts, these files enable the `⊞` side-by-side view.

- **View Log Summary now condenses solver logs** — a `log.simpleFoam`, `log.interFoam`, … written by an `Allrun` run (or any hand-run solver tee'd to a `log.*` file) no longer falls back to the generic last-20-lines tail: the Summary tab now reports the number of time steps and the simulated time range, the final `ExecutionTime`/`ClockTime`, a convergence line when the run converged, and the last step's residuals (initial/final residual and iteration count per field, Courant number(s), cumulative continuity error). Solver logs are recognised by their time-loop shape (`Time = …` steps plus `Solving for …` residual lines) rather than by executable name, so any solver from either OpenFOAM fork works. A run that neither converged nor reached `End` is reported as FAILED, so an aborted run is visible at a glance.

- **Options dialog for the Tools-menu "Run *" actions** — **Run blockMesh… / Run snappyHexMesh… / Run topoSet… / Run setFields… / Run checkMesh…** no longer fire immediately: each now opens a small options dialog with the tool's most common flags as checkboxes and fields (blockMesh/topoSet/setFields: `-dict` with a case-relative **Browse…** and `-region`; snappyHexMesh: additionally `-overwrite`, checked by default; checkMesh: `-allGeometry`, `-allTopology`, `-writeSets` format, `-region`), a free-text **Extra options** field for everything else, and a live **Command** preview showing the exact command line — including the automatic `2>&1 | tee log.<tool>` redirection, which stays out of the user's hands so **View Log Summary** and the Allrun pre-flight keep finding the logs. **Run** is the default button, so Enter runs with the defaults and the flow costs no extra clicks compared to the old confirmation boxes — those pre-flights moved into the dialog: the "case already has results in …" warning appears at the top for the mesh tools, and setFields' three-way "restore 0/, then run" choice became a **Restore 0/ from 0.orig/ first** checkbox (checked by default when `0.orig/` exists) whose `rm -rf 0 && cp -r 0.orig 0 && ` prefix shows up in the preview. Option values are remembered per tool for the rest of the session, and a malformed Extra field (an unbalanced quote) disables Run instead of sending a broken command.

- **Duplicate a tutorial case from Find OpenFOAM Examples** — the Find OpenFOAM Examples dialog gained a **Duplicate this case…** button (enabled, like **Compare with this case**, when the hit lies inside a tutorial case). It opens the familiar Duplicate Case dialog with the tutorial as the source, completing the "search a keyword → find a tutorial that uses it → start my own case from it" workflow without a manual `cp -r` from the installation. The suggested destination is the default case directory (falling back to the home directory — never the read-only installation), the default copy mode is a full directory copy so `Allrun` scripts, `0.orig/`, and `constant/triSurface/` geometry come along, and after copying FoDE offers to open the new case immediately. The **Find OpenFOAM Examples…** action itself is now also listed in the **Case** menu, next to the other Duplicate actions (the same action in both places), since it doubles as a way to start a new case.

### Bug fixes

- **Regenerating one entry of a named parenthesised block no longer drops its siblings' names**: in `regions ( … )` (setFieldsDict), `boundary ( … )` (blockMeshDict), and the new `sets`/`surfaces` lists, an entry's stored raw text began at its `{` — so editing one entry in the tree made every *unmodified* sibling lose its name when the file text was regenerated, corrupting the dictionary. An entry's raw span now starts at its name token (tree-to-editor line highlighting now covers the name line too).

- Fixed a **stale comparison surviving a case switch**: opening a different case while a Compare-with-Case comparison was active left the diff bar, the reference-case parse cache, and the file-list diff marks pointing at the previous case's reference. Opening a different case now clears the comparison; **Reload Case** (same directory) keeps it armed and recomputes the diff marks instead.
